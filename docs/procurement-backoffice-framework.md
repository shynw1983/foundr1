# Foundr1 OS 订货系统业务说明

本文件维护采购、レシート、商品总表与商品比较的领域规则；按当前任务阅读相关章节。执行方式、授权和验证范围统一遵循 [AGENTS.md](../AGENTS.md)。设计计划不等于当前任务的待办。

## 项目定位

Foundr1 OS 的订货系统模块是面向连锁餐饮、加盟店和轻人力门店运营的发注与采购协同后台。它解决的是“门店需要什么”“谁去买”“实际买到了什么”“是否需要门店确认”“价格和供应商是否值得调整”这些日常问题。

系统目前不做招商前台，而是优先做内部运营后台。未来可以继续扩展为加盟店管理、成本分析、供应商协同和商业化 demo。

## 核心原则

### 用语原则

- `发注 / 発注`：门店发起的需求、订单、依赖。
- `购买 / 購入`：采购担当实际执行购买。
- `纳品 / 納品`：商品到达门店或交付给门店。
- `门店确认 / 店舗確認`：门店对数量差异、价格异常、购买不可、采购备注、到货情况进行最终确认。
- `レシート`：日本现场使用的收据名称，不使用“小票”。

同一个动作不能在不同页面用不同词表达。下订单、发注依赖、发注履历属于发注侧；采购管理、购买价格、购买数量属于购买侧。

### 工作边界

- 发注依赖界面 `/os/orders`：门店和门店相关人员使用，负责下单、查看状态、确认异常。
- 采购管理界面 `/os/procurement`：采购人员使用，负责购买、记录实际数量、价格、异常、配送和到货。
- 订单履历界面：管理和复盘使用，负责统计、删除历史、确认/下载レシート。
- 商品总表：管理商品、供应商、规格、价格、适用品牌、购买链接和日本语备注。

## 标准流程

1. 门店用户在发注依赖界面选择门店、品牌和商品。
2. 需求担当默认当前登录用户，并且当前用户在候选人中优先级最高。
3. 采购担当默认店铺 owner，其次 owner/manager，未来可替换为专门采购担当。
4. 用户提交发注依赖后，页面清空当前下单内容，避免误以为还未提交。
5. 系统生成站内通知；配置 Lark 时，同时通知采购担当个人。
6. 采购担当进入采购管理界面处理商品。
7. 采购担当记录实际数量、实际购买价格、购买渠道和异常报告。
8. 只有当采购执行动作完成后，系统才把数量差异、价格异常、不可购买、采购备注转成门店需要确认的信息。
9. 实体店采购可以把已购买商品组成配送批次，并进入配送/到货/门店确认流程。
10. 网店和批发商按供应商维度记录已下单、预计到达日、到货状态。一个订单内多个网店可以有不同到货时间。
11. 发注先维度上传レシート。一次只买了一部分时，后续购买可以上传新的发注先履行记录对应的レシート。
12. 门店在发注依赖界面完成确认。
13. Owner 在订单履历中查看统计、レシート确认、下载、删除历史记录。

## 状态逻辑

### 明细状态

- `未購入`：还没有购买。
- `購入済み`：已购买。
- `購入不可`：本次无法购买，但订单整体仍可完成。
- `配送中`：已进入配送。
- `納品済み`：已到货或已交付。
- `店舗確認済み`：门店确认完成。

### 订单层状态

- `未処理`：尚未开始采购。
- `一部購入済み`：部分商品已购买。
- `購入完了`：全部可处理商品完成购买或标记为不可购买。
- `配送中`：有商品正在配送。
- `納品済み`：已到货但等待门店确认。
- `店舗確認済み`：门店侧确认完成。

完成后不能再操作的按钮统一黑底白字。可操作按钮使用绿色或白底蓝字等明确可点击状态。

采购操作采用乐观更新，`/os/procurement` 会在后台刷新 `/api/dashboard`。新增购买、配送、到货、レシート或门店确认操作时，必须把待处理及近期本地状态合并到刷新结果中，避免旧响应把用户刚完成的 `購入済み`、`配送中`、`納品済み` 或 `店舗確認済み` 状态退回。

## 异常和确认

异常报告用于记录采购现场真实情况。

当前异常类型包括：

- 数量差异
- 价格异常
- 不可购买
- 采购备注
- 规格不一致
- 缺品
- 替代购买

工作流约束：

- 改变实数本身不应立刻产生门店联络。
- 点击配送、到货、购买完成等执行动作后，才生成需要门店确认的信息。
- 价格异常可以有两个处理方式：更新基准价格，或确认后隐藏。
- 不可购买不阻止订单整体完成。
- 采购备注和不可购买内容必须出现在门店确认信息里。

## レシート / 收据

レシート按发注先履行记录管理，使用 `purchase_order_supplier_fulfillments.receipt_photo_url`，不附在商品明细上。上传在采购管理，审核在订单履历。

设计规则：

- 一家供应商一次采购上传一张レシート。
- 如果同一家供应商只采购了一部分，后续再次采购时可以再上传一张。
- 上传照片时前端应自动压缩，避免手机照片超过上传限制。
- 采购管理中如果已购买但未上传，需要明确显示“レシート未アップロード”。
- 订单履历中有レシート确认板块，Owner 可以预览、确认、下载。
- 预览使用浮窗，不新开标签页。

## 权限设计

角色和范围共同决定权限。

- `owner`：全权限。可以删除订单履历、订单明细、联络报告，管理员工、门店、供应商、商品和レシート确认。
- `manager`：运营管理。可以查看大部分数据并处理管理工作。
- 采购担当是工作分配，不代表需要新增 `buyer` 账号角色。当前可配置角色以 `lib/role-permissions.ts` 的 `configurableRoles` 和 AGENTS.md 为准；旧标签不构成恢复该角色的业务要求。
- `store_owner`：加盟店或门店老板。可以查看商品总表，但通常只能查看不能编辑；可以下单和确认本店相关事项。
- `staff`：门店员工。创建发注依赖、查看本店状态、处理门店确认。

权限还要结合 `employee_scopes`。菜单必须按当前登录用户权限显示，不能全量显示后让无权限按钮点了没反应。

## 通知设计

站内通知保存在 `os_notifications`，是每个用户自己的通知。

当前通知场景：

- 发注依赖送信后通知采购担当。
- 网店/批发商到货后通知相关门店确认。
- 配送批次到货后通知相关门店确认。
- 异常或联络报告需要确认时通知相关人员。

Lark 是可选增强；集成入口在 `lib/lark.ts`，发送失败不能阻断核心操作或站内通知：

- 内部员工私信可使用 `open_id` / `user_id`；配置所需 Lark 权限后，owner 可按邮箱查询员工 Lark 用户 ID。
- 发注通知可以发给采购担当个人。
- 外部加盟店老板如果不在公司通讯录里，个人 open_id 会受到限制；更适合用门店群 webhook/chat_id。
- 未来需要实现门店绑定 Lark 群，发注通知同时发给采购担当个人和门店群。

## 商品总表

商品总表是运营基础数据中心。

商品数据应保留运营含义。常用字段包括 `name`、`japanese_note`、`category`、`subcategory`、`unit`、`package_quantity`、`package_quantity_unit`、`reference_price`，以及发注先选项、包装规格和购买 URL。字段名以当前 schema 与读写代码为准；历史 `package_spec` 在 `scripts/apply-schema.mjs` 中有转入 `variant_name` 后删除的迁移，不应仅因旧文档提及而重建。

重要信息：

- 商品名
- 日本语备注：中文商品名或进口商品给日本员工看的补充说明。
- 大分类 / 小分类
- 单位
- 数量与数量单位
- 规格
- 参考价格
- 规格单价
- 保管方式
- 原产国
- 适用品牌
- 主要发注先 / 备用发注先
- 购买链接
- 图片

规格计算规则：

- 如果填写了数量，优先用数量计算单价。
- 如果没有数量，再用重量规格计算。
- 克和千克可自动换算。
- 毫升和升不参与重量换算。
- 例如一箱 200 个、每个 1500 ml 的杯子，应按 200 个算单个成本，不能按 1500 ml 算。

用户可以选择商品卡片右侧显示哪些基本信息，选择保存在 `employees.ui_preferences` 里。选择太多时必须换行或压缩布局，不能横向溢出。

## 供应商管理

供应商可以是：

- 实体店
- 连锁超市
- 网店
- 批发商
- 平台店铺

供应商资料应包括：

- 名称
- 类型
- 地址
- 电话
- 联系人
- 营业时间
- 购买 URL
- 备注
- 可信度

商品总表选择供应商时，应支持快速新增供应商的简易弹窗。

网店和批发商在流程上更接近“提交订单后等待到货”，不是“到店购买后配送”。因此它们按供应商维度记录已下单和预计到达日。

## 订单履历与报表

订单履历不只是明细列表，需要用于复盘。

当前包括：

- 订单履历
- 商品使用量排行
- 明细一览
- レシート确认
- 店铺筛选
- 全店汇总
- 时间区间选择
- 月份快速选择和自定义日期范围

Owner 可以删除订单、订单明细和联络报告。

## 现场记录

现场记录用于任何人提交现场发现：

- 新商品创意
- 供应商现场发现
- 更便宜渠道
- 需要后续讨论的商品

它是意见和素材收集板块，所以所有角色都可以参与提交。记录支持照片、批注、状态和删除权限控制。

## 商品比较

商品比较用于把现有商品与候选商品做成本对比。

设计规则：

- 现有商品按分类选择，避免所有商品堆在一张列表里。
- 候选商品有独立商品名、候选供应商名、购买链接、原产国、价格、规格数量、单位和备注。候选供应商允许自由输入；在线和进口商品的购买 URL 必须保留。
- 国内商品默认日元。
- 海外进口品输入外币金额和币种，目前支持人民币。
- 汇率按当前实际汇率换算成日元。
- 运费按每 kg 运费乘以进口总重量计算。
- 如果商品单位是箱，进口比较时需要填写每箱重量。
- 克和千克自动换算，毫升、升、个不做重量换算。
- 历史结果支持编辑、复制后重新比较、归档、恢复和删除。

## 商业化方向

这个系统对麻辣烫、奶茶、轻餐、外带和依赖食材堆叠的行业有优势，因为这些行业成本由 SKU、规格、供应商和购买频率决定。

更适合强调的价值：

- 降低漏买和错买。
- 让兼职或加盟店也能按标准流程采购。
- 记录价格异常与供应商变化。
- 形成商品单价和历史趋势。
- 用レシート和实际购买记录支撑成本复盘。
- 给总部看各店使用量、异常率和高成本商品。

## 暂缓但已记录的事项

- 外部成员/加盟店老板 Lark webhook 群通知。等待有门店外部群后再验证。
- 波动型价格的参考价格策略和历史趋势图。蔬菜等季节波动商品可考虑“参考区间”而不是单一基准价。
- レシート OCR 自动识别。
- 专门采购担当角色细分。
- 安全库存和自动补货提醒。


## 采购与库存扩展基础（2026-10-08）

本节保留第一阶段的实现及迁移说明。第一阶段已于 2026-10-08 发布（`caee658`），旧商品目录按原有有效门店范围保留；下述迁移说明记录该次发布的数据保留约束。

- 现有商品总表的具体规格商品 ID 作为 SKU 身份。同名商品不能代替 ID；保留唯一名称旧客户端，歧义返回刷新/指定 ID。
- 品牌适用范围与门店公开范围独立。`catalog_visibility` 为 `internal`（仅本部）、`brand_stores`（适用品牌门店）、`selected_stores`（指定门店）；指定门店通过 `product_catalog_store_grants` 保存。公开本身不扩大员工门店范围。
- 商品全局 `is_orderable` 与匹配品牌的发注许可共同控制新增发注、追加、换品和残数拆分。停止发注不删除既有库存、采购履历或阻止既有事项的收货/确认。
- 门店目录不返回本部参考成本、进口成本、上游发注先和购买链接；任意 SKU 价格履历仅本部可读。本店已有交易的实际成交价与凭证仍按门店范围保留；总部供货价和上游成本分账尚属后续阶段，不能将其宣称为已完成的加盟结算。
- 商品照片按精确存储路径检查公开范围；已不公开但本店已有库存/采购记录的商品，保留必要的识别图片。
- 数量、价格异常确认保存当时的事实快照与审计，不修改实购数量/价格。新客户端提交所见快照，事实已变化时返回 409；重复确认不重复登记相同审计。事实再次改变会产生新确认要求。 旧审计记录没有保存事实快照，迁移不反推确认；仍存在差异的旧事项可能需要重新确认。
- 数量统计区分需求与记载购买量；未记录的实购数量为未知，不以需求量代替，也不计算金额。名称为「発注・購入数量」，不能用于推算食材真实消耗。
- 盘点数量和异常观察分开：异常不刷新实际盘点时间；人工不足报告也进入发注确认提示。数量必须为明确数值；盘点单位变更清空旧数量及实数确认时间。盘点写入带预期单位，单位已变更时返回 409，旧页面需要刷新。
- `inventory_checks.count_unit` 保存每次记录的单位；迁移前历史单位未知，显示「単位未記録」，不按当前配置回填。

迁移文件为 `db/migrations/20261008_procurement_foundation.sql`，仅新增列、约束和授权表，保留原采购/库存事实。旧商品默认仅本部可见：发布前必须盘点并确认需要向门店公开的商品与目标门店，不能直接全量公开。先在隔离数据库验证迁移和授权矩阵，再对获授权的目标应用该迁移，并用 `npm run db:check` 核对所需列；本次不得借由全量 `db:push` 顺带应用无关 schema 改动。

如果本次获授权保留现有门店的原有目录范围，应在基础迁移之前先执行 `db/migrations/20261008_preserve_existing_product_catalog.sql`。在同一次事务中先锁定并快照旧 SKU 与现有门店的有效品牌配对，再添加公开字段与明确的逐店授权；基础迁移的其余变更可紧接执行，最后一起提交。脚本独立执行时自带事务；合并执行时移除两个文件各自的 `BEGIN`/`COMMIT`，仅保留一个外层事务，不直接拼接带事务的脚本。不要先执行基础迁移再重建旧范围：一旦 `catalog_visibility` 已存在，保留脚本明确拒绝执行，避免覆盖总部后续配置。

保留脚本只将已有有效门店配对的旧 SKU 设为 `selected_stores`，不会设为自动覆盖未来门店的 `brand_stores`；新增门店没有继承授权，新增 SKU 仍默认 `internal`。旧查询使用既有 `product_brand_usages` 关联，不要求 `brand_scope` 已标记为 `specific`，因此脚本将有既有品牌关联但标记未设置的旧 SKU 规范为 `specific`；不添加或删除品牌关联，不改发注停止标志。没有有效品牌配对的 SKU 保持仅本部可见。空员工门店范围不因保留快照而获得访问权；`store_owner` 不能用于推断直营或加盟身份。

原采购接口没有使用品牌关联的 `is_orderable` 标志。如果存在原先可见而匹配品牌全部停止发注的门店/SKU 配对，脚本中止并要求审阅，不能静默清除标志或阻断原有发注。旧总部接口也曾接受未配置品牌的商品；这类商品需要独立确认适用品牌，不能借由兼容迁移猜测为共通。脚本在提交前以双向差集校验迁移前后的门店/SKU 可见配对，任何新增或丢失都会回滚；已有库存与订单事实继续按原门店范围保留。保留旧实际范围是过渡行为，不代表已确定最终加盟商品公开清单。

验证包含商品公开/停止/目标门店、目录脱敏、确认前事实变化、重复确认、无权限、单位变化和未知数量。`scripts/tests/procurement-foundation-db.mjs` 在隔离 PostgreSQL（PGlite）上执行真实迁移与核心 API SQL，不读取 `DATABASE_URL`；通过 `FOUNDR1_PGLITE_MODULE` 指定临时运行库。线上账号、现有数据的公开配置及生产数据库分支仍需单独验收。

`scripts/tests/product-catalog-preservation-db.mjs` 单独验证旧范围快照、既有品牌关联的范围规范化、无品牌关联 SKU 保持内部、未来门店/新 SKU 不自动公开、二次执行拒绝覆盖和品牌停止标志造成的原子回滚；同样只使用隔离 PGlite，不读取生产连接。

第一阶段发布时尚未实现（菜单 SKU 关联与补货确认已在下文第二阶段实现）：菜单/选项与 SKU/配方关联、补货风险待办与通知、实际到货入库、库位移位/调拨/损耗流水、分次采购履行与多份收据、批次期限、销售消耗和补货预测。

## 菜单关联 SKU 与补货确认（2026-10-08，第二阶段本地实现）

本阶段在已发布的商品公开/发注控制基础上，接通菜单销售状态、库位不足报告与门店发注。代码及迁移草案不代表已部署或已应用生产数据库。

- 本部在 `/os/menus` 的商品或选项编辑区域单独保存「在庫・発注の商品関連付け」。`menu_product_links` 按具体菜单/选项 UUID 关联一个或多个具体规格 SKU；不以名称、共享销售状态键或既有制作参考说明猜测关系。关联不进入 Uber 权威 payload，不修改客户菜单显示文字、销售可否或售价，因此本阶段不改变 maamaa/nanacha 品牌网站的数据契约。
- 关联维护需要 `owner`/`manager` 加 `menus.edit`；目标必须是品牌标准菜单，SKU 必须适用同一品牌或已明确为共通。内部商品和停止发注商品仍可关联用于追溯。保存携带所见 SKU ID 集合，事实已变化返回 409，不能覆盖另一个编辑器刚保存的关联。菜单关联的 SKU 不可删除，可停止发注；删除菜单时仅删除其关联，不删除采购商品或采购/库存事实。
- `/store/menu` 点击总体「残りわずか」/「売切」并成功保存后展开「補充確認」。单平台售罄覆盖不构成整体采购缺货；配方依赖造成的下游售罄不再推断每个下游 SKU 缺货。原生入口已有的总体售罄也由同一读模型读取；本阶段没有新增原生 widget 的低库存/补货卡。
- `/api/replenishment` 按当前门店范围读取当前总体销售状态与库存不足信息，不保存额外任务副本。按门店与准确 SKU 合并来源，保留每个菜单与库位的数量、单位、盘点时间/可信度；不同库位或单位不相加。未关联菜单单独提示本部配置；对门店隐藏的 SKU 不返回其 ID、名称或成本。门店终端只读，不显示无权限的发注或本部配置入口。
- 库存安全值以下、人工 `low`/`out` 观察均进入检查，未确认或过时数量仍明确标注。观察、补货确认、发注与到货流程均不伪造盘点数量，也不自动恢复销售状态。
- 展示同店同 SKU 尚未最终确认的发注（`requested`/`purchased`/`in_delivery`/`delivered`），排除 `received`、`unavailable` 及 `RCPT-` 收据记账事项。需求量与记载购买量分开，未知实购量/单位保持未知。已有发注只提示，不能宣称食材已到货或缺货已解除。
- 创建补货发注复用 `/os/orders`。入口按门店与具体 SKU ID 预选，保留已有草稿，数量留空，必须明确选择 1–999 的整数发注单位数。SKU 未公开、停止或已更换单位时要求检查；有未受领发注时必须确认仍需要追加。
- 补货提交携带当时的未受领明细 ID 集合。所有新建发注在同一事务中对门店/SKU 排序加锁；补货路径在锁后的新快照检查明细、单位和当前目录授权，变化返回 409 不生成订单或重复通知。编辑原发注、采购追加、换 SKU 和拆分残数也按既有订单锁与门店/SKU 排序锁复查当前事实，再将相关明细、实购和价格记录原子提交；纯确认仍保留单 SQL 的事实快照核对。新订单与明细原子写入；通知在提交成功后发送。`purchase_orders.replenishment_source` 保留来源门店/SKU与所见明细信息，不将技术 ID 拼入门店备注。

迁移草案 `db/migrations/20261008_menu_product_links.sql` 仅增加关联表与来源字段，不回填推测的菜单关系。独立 PostgreSQL 测试验证关联/删除约束、品牌/权限、陈旧保存、风险去重/脱敏、明确数量与重复发注防护。生产发布前仍需在授权的生产数据库副本验证，再应用该特定迁移并运行 `npm run db:check`；不得用全量 `db:push` 顺带执行其他 schema。

后续扩展仍包括每份配方耗用与条件、实际到货入库、移位/调拨/损耗、批次保质期和销售消耗预测。当前「補充確認」是人工核对入口，不是自动采购或库存扣减。

## 购买、使用与清点单位对应（2026-10-08，本地扩展）

同一个具体 SKU 的 `products.unit` 是发注/购买单位。`inventory_unit_conversions` 保存一个购买单位对应的多个使用/棚卸单位，例如 1 袋 = 20 個、1 袋 = 4 个 `1/4袋` 单位；整数分母的分袋单位以独立命名单位记录，1 个 `1/3袋` 不会改写成 0.33 袋。原有明确包装数量/数量单位也可提供换算参照，与额外关系冲突时不能保存。系统不按商品名称、同名商品或 kg/g 等单位名称推测关系。

本部维护对应关系。门店只能查看其可见 SKU 的运营单位并选择清点单位，不能借此读到上游成本或修改本部对应关系。商品编辑携带打开编辑器时的单位配置快照；购买单位改变时需显式复核关系，陈旧保存返回 409，保留下书き。省略换算快照的旧清点网页仍按库存配置的字面单位记录实数；待旧页面刷新到新版本后，可收紧期望快照要求。当前 Android widget 管理菜单销售状态，不读取这套库位实数接口，本阶段不改 APK。

库存始终保存实际清点单位与数量；换算只用于展示参照，不自动写回库存或发注数量。新清点记录保存当时的购买/清点对应快照，旧记录快照保持未知，不按今天的设置反推。对应关系变化不删除或重算已记录的清点数量；界面提示再确认，历史购买单位换算仍以历史快照计算。改变库位清点单位延续原规则：清空当前数量与实数确认时间，历史记录保留。

迁移草案 `db/migrations/20261008_product_unit_conversions.sql` 增加关系与快照字段，将实际/安全库存和历史清点数量扩至 `numeric(18,6)`，保持现有数值。清点接受六位以内小数及可精确表示的分数；不能有限表示的分袋数量通过命名的 `1/X` 单位记录，不静默舍入。购买包装字段沿用既有精度，不允许保存后与手工关系产生舍入冲突。本地 PostgreSQL 测试检查关系权限、旧客户端保存、并发配置变化、单位精度与历史快照；迁移尚未应用生产，发布前仍需授权的生产分支验证和特定迁移应用。

## 棚卸、补充发注与实际入库联动（2026-10-09，本地扩展）

目标流程为「实数棚卸 → 不足确认 → 补充発注 → 購入 → 納品 → 门店核对数量和库位并入库 → 再判断库存是否不足」。本节实现与迁移草案尚未发布；前述第一阶段发布状态不变。

- 入库在 `/os/inventory` 和 `/os/orders` 登记。入口只读取权限范围内已 `delivered` 或 `received` 的具体采购明细；原来的 `店舗確認`、差异确认及采购数量编辑本身不增加库存。已完成门店确认但未登记入库的明细仍可选择。收据记账事项、购买不可和没有具体 SKU 的临时商品不能作为自动入库来源。
- 每次明确输入实际收到的购买单位数量，选择同店同 SKU 的保管库位。可以分批到货，也可以将一个采购明细分次放入不同库位。累计入库数量不能超过已明确记录的实购量，未记录的实购量或单位不以需求量代替。累计历史入库按登记时的购买单位分别显示；单位未知、改变或与历史流水不一致时，待入库残量保持未确认，不能将旧单位数值标成新单位。实际单位必须与该 SKU 当前购买单位一致，库位单位通过明确的对应关系转换；关系未知或已变更时先核对配置并重新清点。
- 操作人必须选择「本次到货尚未计入库存」或「当前清点已包含本次到货」。前者在明确的库存余额上加本次入库量；后者只关联已经包含的采购事实，不再增加库存。首次库存总量未知时不能按零起算，先清点包含到货后的实数，再用已包含方式关联采购。重复网络提交复用同一请求 ID，不重复登记或增加库存；同一 ID 携带不同内容返回冲突。
- `inventory_items.current_quantity` 和 `count_conversion_snapshot` 保留最后一次物理清点事实。新的 `stock_quantity` 和 `stock_conversion_snapshot` 保存最近清点加后续入库计算的余额；入库不改 `last_counted_at`、清点人或历史清点。页面分别展示当前计算库存、最后清点实数与入库登记时间，并说明当前没有自动扣减使用量。异常观察不将未清点的库存伪造为零。
- 实数清点同时校准物理数量和计算余额。`stock_revision` 随清点、入库、库位单位重置递增；清点与入库提交携带所见版本，期间发生更新返回 409，保留输入并要求重新核对。已有旧网页省略版本，仅在无入库且计算余额等于最后清点数时允许原有字面单位清点；有入库后要求刷新页面。
- `inventory_stock_receipts` 保留稳定采购明细 ID、本次购买数量、目标库位、当时换算、前后余额、登记方式、操作人和时间。历史快照不按今天的包装关系重算。库存不足以计算余额重新判断；入库后仍低于安全库存继续提示。质量或损坏报告保留待核对，菜单售罄/残りわずか不会自动改为可销售。
- 本店已有采购和库位中的停售或后续不公开 SKU 可登记原交易入库；不因此扩大目录公开范围或暴露本部成本。入库需要 `module.inventory` 和可写登录及店铺范围；终端可查看，不能登记采购入库。已有入库事实的来源禁止换 SKU、改数量/单位、拆分、撤回购买、逆转配送或删除；普通差异审核、正常门店确认仍独立进行。实购更正、退货和冲销属于下一阶段，不覆盖已登记入库流水。
- 配送批次的到货/门店确认通过一条原子 SQL 同时更新批次及明细；陈旧请求不能将配送中的商品直接确认为已收货，重复到货不能把已确认明细倒退。这个状态保护不会自动执行入库。

迁移草案 `db/migrations/20261009_inventory_receipts.sql` 添加余额字段及入库流水。在字段首次创建时以已有明确清点数量及其已保存换算初始化余额，未知仍未知，不重建历史入库。重复迁移不重置新余额。发布前先对授权目标的数据库副本验证三个待发布迁移，再显式应用它们并运行 `npm run db:check`；不使用全量 `db:push`。本阶段没有加入销售耗用、出库/调拨、整店盘点任务、入库撤销、批次期限或加盟结算。

旧版本的缺货观察曾将 `current_quantity` 写为零但保留旧清点时间。迁移保留原值，不将它反推为物理清点；初始 `stock_revision = 0` 的数量在界面标为「元の記録数量」并要求重新清点。新清点建立明确的实数及换算，才进入正常的清点/入库计算显示。此次不推测修正旧库存数据。

## 简便／粗略操作模式（2026-10-09，实现与发布契约）

本次完整发布包含菜单 SKU 关联、补货确认、单位换算、清点与采购入库联动，以及本节简便模式。此前各阶段的“本地／未发布”说明是当时的验证记录；最终部署和生产迁移结果以本次 release 证据为准。

- `/os/inventory` 默认「かんたん確認」，可切换「数量で棚卸」，本机记住模式。日常按库位或搜索范围选择「足りる／残りわずか／ない」，并显式批量保存。未操作商品不自动视为正常；“当前显示已看过，其余够用”只填补当前范围的空选择，保留草稿和已有负面报告。
- 目测状态、操作者、时间、当时库存／单位／安全值及独立确认版本分别保存，不修改物理清点或账面数量。当前库位24小时内、库存及配置未变的“够用”可压住该库位较早数值引起的不足提示，不关闭菜单销售状态或其他库位的报告。入库／配置变化后正常目测需再查看；负面报告继续待核对，新的实数清点或明确观察可取代。质量、破损和过量报告独立保留。
- 可选袋数等估算支持整单位与约半单位按钮、自由估算数或“少量”。估算按原购买单位保存并标为目安，不作为实数清点、账面数量、准确耗用或自动采购量。单位变更需复核，不能将旧袋数改贴为箱数。未保存观察按门店暂存在本机；冲突保留输入，显式复查后再提交。批量提交最多500个明确ID，库存／配置／确认版本必须全部匹配后才原子保存。
- `/os/orders` 支持本店常用发注清单，保存准确SKU、明确整数发注单位数和当时单位；后台按门店、权限及当前目录校验。模板主动追加到草稿，保留既有数量、空数量、备注和补货来源；失去公开／发注权限、单位已变或SKU消失的条目不暴露原身份，也不借同名SKU替换。模板是草稿，不自动生成发注。重名保存返回冲突，不覆盖旧清单。
- 快捷入库选择已到货的购买明细。唯一有效的同店同SKU库位可见预选，多库位需选取；操作人点击“本次尚未入库数量已全部收到”后才采用已记录实购余量。少到、分批或分库位在详细区明确输入；购买需求量不冒充实收量。每个明细独立登记，首版没有跨明细一键批量入库。
- 入库直接选择“新到货加入库存”“清点已包含只登记”或“仅登记本次到货，总库存待确认”。第三种 `unverified` 保存已知购买数量与其真实历史单位、具体库位，将账面总量及换算快照标为未知，不依赖今天的包装关系或假设旧余额为零；流水的清点数量和换算快照为空，原物理数量及清点时间不动。版本递增保护旧清点草稿；以后实数清点建立总量时不再补加旧入库。原精确两种方式的换算及已知余额要求保持。
- 入库流水累计不超过同一稳定购买明细的已知实购量；不同单位不能混减，重复请求不重复入库，所有来源及库位范围再次核对。实购量或单位未知时先完成物流到货确认，保留数量待核对／待入库，不登记伪造数量。操作失败、结果未知及状态冲突按原稳定请求ID重试或复核，成功记录不覆盖后来的草稿。

本次追加迁移为 `20261009_inventory_quick_checks.sql`、`20261009_inventory_receipt_unknown_balance.sql` 和 `20261009_procurement_order_templates.sql`，与前述三个待发布迁移一起，在生产副本上按顺序执行两遍并比较原业务事实；正式发布只应用这些特定迁移，不用全量 `db:push`。

日常防缺货用简便巡查；首次建账、定期校准、贵重食材及差异处理按需使用精细清点。当前仍无销售自动耗用、出库／调拨、批次期限及库存冲销；这些不能由目测或到货事实推断。
