# 库存采购与门店操作说明

更新日期：2026 年 10 月 18 日。适用对象：门店员工、店长、采购担当和总部管理人员。

**10 月 18 日实现补充（待迁移、发布验证）**：员工通过 `/store/replenishment` 报缺并查看进度；已保存的库存风险和菜单缺货信号汇入同店同 SKU 的需求池。负责人在 `/os/replenishment` 核对、追加、减量、暂缓或关闭，确认后生成正式发注，实际购买仍在 OS，收货仍在 Store。重复报告不累加购买量；购买完成不自动判定需求已满足。详见 [共享补货需求池规则](store-operation-rules.md#shared-replenishment-demand-pool-2026-10-18-implementation)。下文“当前操作”及功能表保留 10 月 12 日操作快照，员工申请入口的旧限制在新版本发布后由本段取代。自动建议采购量、接单扣减和自动停售仍不属于本次实现。

这套流程的目的，是提前发现不足、及时保护多平台可售库存、集中购买并准确入库，同时减少员工每天逐项精细录入的负担。SKU、配方和规则由 OS 管理；员工在 Store 做检查、清点和收货。

**已经确定的新规则：接到有效订单就立即扣减共享可售库存，开始制作时不再重复扣减。当前实现仍按制作时点扣减，接单扣减、自动停售和完整补货需求池尚未接通。** 下文明确区分当前操作和目标流程；标为“待实现”的步骤目前不能作为已上线功能使用。

目标全流程：总部设置 SKU 与配方 → 门店建立实盘起点 → 接单扣可售 → 不足时停售与补货需求合并 → 采购担当购买 → 门店实际入库 → 重新核对可售与平台状态 → 定期清点校准。

## 总部首次设置

### 建立商品与单位

1. 在 OS 商品总表维护稳定 SKU，填写名称、图片、品牌、保管方式和发注先。质量、用途或配方不可互换的商品分别建 SKU；仅本次包装变化的同类食材通常沿用原 SKU。
2. 明确购买单位、清点单位和使用单位。例如购买按袋，清点及使用按个，明确保存「1 袋 = 20 个」。不要根据商品名、运输重量或参考价格猜换算。
3. 进口食材每批规格变化时，使用本次包装规格或包装模板，保存当时的换算。旧入库和旧清点不会跟随今天的默认包装重算。
4. 设置向哪些品牌和加盟店公开，以及是否允许发注。公开、可采购、菜单可售分别管理；停止新发注不删除既有库存或阻止既有到货登记。

### 建立菜单配方与本店库位

1. 在 OS 关联准确的菜单或选项与 SKU。采购识别关系用于说明“买哪个商品”；用量配方还须说明“每份扣多少”。只有关联 SKU 而没有定量配方，不能准确扣数量。
2. 每项用量选择准确、预计或未测定。准确用量用于明确扣减；预计和未测定用量保留预测依据，不冒充准确实数。确实不额外耗用食材的选项可以明确设为空配方；漏配方不能当零耗用。
3. 在 OS 库存保留每店的设备、位置和库存项目，例如「冷冻柜 A／上层／芋头」。同一 SKU 可以在多个位置，但订单使用哪个位置要明确；当前多个位置不会自动轮流取货。
4. 员工第一次在 Store 清点真实数量，建立库存起点。总数量不知道就保留“未确认”，不要填零。
5. 设置安全库存。补货目标、覆盖天数、供应商起订量及自动停售规则属于需求池升级需要完善的配置，当前没有完整建议量计算。
6. 启用现有订单联动前核对配方、单位、库位和订单身份。当前启用只能得到现有制作时扣减行为，不能得到接单即扣或自动停售；启用前历史订单不批量补扣。

## 员工每天检查与清点

### 日常粗略巡查

1. 打开 Store「在庫確認」，确认当前门店和操作人。
2. 按保管位置找商品，或搜索商品名称。
3. 默认使用「かんたん確認」，选择「足りる」「残りわずか」「ない」。先标出不足，再将真正看过的其他商品标为够用；不要对未看过的商品批量确认。
4. 有需要时附上“约半袋”“约两袋”或“少量”；这是目测估计，不改变实盘或账面数量。
5. 保存本次看过的项目。保存前库存或单位已变化时，重新查看现场，确认最新依据后再提交。

**粗略“ない”是库存报告，不代表菜单已经停售，也不代表其他平台已同步。** 缺货时由具备菜单操作权限的当班负责人处理销售状态。

### 需要时做实数清点

首次建账、关键食材、定期校准、库存差异或包装混用时，切换「数量で棚卸」。员工输入现场实际看到的数量和单位，核对换算预览再保存。

- 明确「1 袋 = 20 个」，准确半袋可记录为 10 个；仅目测约半袋，仍使用粗略模式。
- 非有限小数的分袋数量不要随意写成 0.33。可以直接数个数，或由总部配置本库存项目能够准确保存和换算的「1/3 袋」命名单位。例如库存按个保存、每袋 20 个时，三分之一袋仍无法准确换成有限小数个数，应数个数或保留粗略估计。
- 多种包装混在同一位置时，统一用个数、克等明确基准单位清点，不输入无法区分批次的总袋数。
- 质量或破损问题单独报告，不通过修改数量来代替原因记录。数量存在也不意味着能够销售。
- 冲突提示出现时保留输入，重新核对单位、库存及当前操作人；不要绕过冲突连续提交。

## 接单扣减与多平台停售

### 目标流程中的有效订单

| 来源 | 扣减时点 |
| --- | --- |
| POS | 交易提交为有效订单、完整明细保存后 |
| 桌台点单 | 店铺接到有效点单后；后付订单不必等付款 |
| Web予約 | 付款确认、形成有效订单后；支付前草稿不占正式库存 |
| Uber Eats、Rocket Now、出前館 | 店铺接到有效原始订单后；必须准确识别商品、选项、份数及原单身份 |

上述是待实现的统一规则。三平台当前导入仍缺少可信自动身份映射，不能只按相似名称扣库存；当前人工确认原单的映射只覆盖那一单。仅收到通知但还没有完整订单明细，也不能假定已准确扣完所有 SKU。

份数与每份选项数量都要保留。例如两份菜、每份选 3 个芋头，本次扣 6 个。迟到导入或改单须保留原单时间和冻结依据，不能把旧订单重新当新订单；实盘也不能被默认视为已经覆盖尚未制作的占用。

### 目标流程中的三个数量

员工清点的是实物数量；系统另外保留尚未制作订单已经占用的数量和可售数量。已占用商品还在店里，但不能再卖。

| 时点 | 理论实物数量 | 待制作已扣数量 | 共享可售数量 |
| --- | ---: | ---: | ---: |
| 芋头清点 11 个 | 11 | 0 | 11 |
| 有效订单买 1 个，尚未制作 | 11 | 1 | 10 |
| 此时再次清点，眼前仍为 11 个 | 11 | 1 | 10 |
| 取出该芋头并投入制作 | 10 | 0 | 10 |

清点不能把已占用的 1 个重新释放为可售。未制作就取消时释放原占用；已经使用食材后取消或退款，保留耗用。退款金额变化本身不证明食材回来了。部分取消或改单按准确明细处理，不一律回补整单。

### 最后一个芋头的目标流程

1. 实盘 1 个，待制作占用为 0，可售为 1。
2. Uber 有效订单买 1 个：共享可售立即变为 0，并保存原单和冻结用量；重复导入只处理一次。
3. 对已启用自动停售的精确 SKU，阻挡其明确关联的菜单或选项；同步向所有适用平台发送停售。
4. 补货需求池更新本店芋头的同一条需求，保留“订单耗尽”来源，不逐单新增采购单。
5. 开始制作只更新占用与实际耗用状态，不再扣第二次。
6. 未制作取消可释放这 1 个，但恢复销售仍须检查质量、人工停售及其他缺料原因。

OS 库存扣减完成和平台停售成功是两个结果。各平台应分别显示同步中、成功或失败；失败保留重试与告警。Bridge 采集及平台执行存在时间差，不能承诺三平台瞬间同时关闭或绝对没有并发超卖。自有下单入口也需要在提交时检查共享库存，不能只靠菜单列表显示。

停售要按“还能完成多少份”判断，不必等原料数量变成零。例如每份底料需要 0.3 kg，只有 0.2 kg 就不能再接一份。多个菜单共用一种原料时分别核对有效配方与条件；必需原料不足阻挡对应菜品，选配原料不足阻挡相应选项。安全库存用于提前补货，能否完成一份用于可售判断，两种阈值不混用。

### 现阶段最后一份被订单占用时怎样操作

当前还没有上述自动闭环。员工立即通知有 Store 菜单权限的当班负责人，由负责人设置总体缺货并查看各平台同步结果；普通员工仍可记录不足报告。

**不要把尚未制作、实物还在店里的 1 个假清点为 0。** 现有制作时耗用再运行会产生错误扣减。当前实盘始终按真实物理数量填写；停售另走销售状态流程。只有平台确认成功，才算该平台完成停售；失败的平台需要负责人继续处理。

## 补货需求池与集中采购

### 当前补货核对

有权限的负责人在 OS 库存或 Store 菜单打开「補充確認」。同店同 SKU 的菜单和库位风险已经合并，并展示已有未受领发注及到货未入库信息。

发注前先检查其他库位、既有发注和已到未入库商品。现有风险读取主要包含不足来源，不能把其中的库位行当作全店总库存；当前页面不自动计算建议采购量。创建补货发注会进入 OS 草稿，购买单位数量留空，须人工填写；发现已有未受领事项时先确认是否确实需要追加。

普通员工的 Store 库存页目前还没有补货申请入口。因此员工发现不足后由店长统一核对并提交，不让每个人分别建采购单。

### 需求池的目标规则

**一个门店、一个准确 SKU 同时保留一个开放补货事项。** 多次订单、巡查或缺货报告只更新缺口、来源和紧急程度。一个需求可以由多次采购、多供应商、多批次到货满足。

池里需要显示：门店、SKU、可售库存及可信度、全部相关库位、补货目标、未处理发注、已确认购买及预计到货、未入库量、建议购买量、负责人和处理记录。应按门店权限展示；跨店合批购买仍保留每店分配。

先把能换算的可用库位统一到明确基准单位。正常备餐时限内能取用、数量和质量已确认的其他库位库存，可纳入有效可用量；必须解冻或备料且赶不上出餐的，作为后备库存并提示处理。工作位不足而其他库位有可取库存时，先补位，不直接采购。这些多库位取用规则属于目标流程，当前仍须指定订单使用位置。

即时可售和采购计划使用不同时间范围。采购计划先合并本店在补货窗口内能调动的正常库存，扣除待制作占用，排除质量隔离和未知数量，得到“补货计算可用库存”；不要只减工作位数量，造成后备有货仍重复购买。

建议购买量的初期规则：

```text
待补数量 = max(0, 补货目标 − 补货计算可用库存 − 可按时到货的已确认未入库数量)
建议购买量 = 按本次包装换算，并按发注先的最小购买量取整
```

这里的在途必须有真实确认数量、本批规格和有用的到货时间。只提交了发注、实购量未知或赶不上缺货时点的货不能自动抵扣当前缺口。预测不可靠时显示“需核对”，不编造精确袋数。

例：目标 40 个，本店合计可用于补货计算的库存 10 个，没有可按时到货的在途；每袋 20 个，整袋购买。缺口为 30 个，建议购买 2 袋。若已确认有 1 袋按时到货，新增缺口为 10 个，建议再买 1 袋。需求池不会因两次报告分别生成两笔“买 2 袋”。这些建议量目前待实现，现阶段由负责人核算。

需求是否不足与采购进度分开显示：待核对、待采购、采购中、购买不可、在途、部分入库、到货待核对、已满足。已经购买但尚未到货时仍可能缺货；“購入不可”或采购单显示完成，也不能关闭未满足的需求。

## 发注与实际购买

1. 店长或获授权人员在 OS「発注依頼」选择本店准确 SKU、购买数量、希望到货时间及采购担当。当前补货发注要求 1 至 999 的整数购买单位；清点可使用小数不代表所有采购入口支持小数。
2. 采购担当在 OS「購入管理」集中处理，可以按发注先组织购买。需求量、实际购买量和实际到货量分别保存，不用需求量填补未知实购量。
3. 只买到一部分时记录真实数量，复核是否拆出剩余购买需求；购买不可时记录原因并安排备用发注先或其他方式，不将缺口视为解决。
4. 本次进口包装不同，核对本批内容与换算。一个购买明细已冻结包装后，不把另一个规格覆盖上去；同次买到两种包装时分别保留具体明细。
5. 实体采购登记配送批次；网店及批发商按发注先登记已下单、预计到达日和到货。不同发注先或批次可以有不同时间。
6. 当前同一订单、同一发注先只有一个当前レシート记录，再次上传会替换该记录的收据引用。多次购买先保留所有原件及照片，交管理人员整理，不把单张系统记录当作完整历史。按每次实际履行保留多份收据是业务目标，当前尚未完整实现。

购买和付款都不增加本店可用库存。真正到货后才由门店登记；采购完成也不自动恢复菜单销售。

## 到货入库与门店确认

### 员工实际操作

1. 打开 Store「納品・入庫」，确认门店和操作人。
2. 选择真实到货对应的购买明细，核对商品、实购量及已经登记的入库量。
3. 选择实际保管位置。找不到本店 SKU 或位置时交总部补配置，员工不临时创建一份同名库存。
4. 核对本批包装。规格相同可复用已有模板；不同就确认本次内容量及转换后的个数或重量。
5. 一次全到可使用页面快捷数量；部分到货在详细区域填写本次实到量。分到两个位置的，分别登记各位置实际放入量，累计不得超过真实购买数量。
6. 依据下面表格选择登记方式，检查库存变化预览后提交。
7. 已知数量的 Store 入库会与适用的「店舗確認」一起保存。同一购买明细只到部分时仍待确认，累计实际入库等于该明细实购数量才确认该明细；整批所有关联明细确认后才完成整批确认。

### 选择正确登记方式

| 现场情况 | 选择 | 保存后结果 |
| --- | --- | --- |
| 原余额已知，这批新货尚未计入库存 | 新到货加入库存（add） | 增加本次准确入库量 |
| 最近实盘已经把这批新货一起数过 | 清点已包含，只登记对应到货（included） | 不再加一次数量 |
| 已知到货购买量，但总库存或本批换算不能确定 | 登记到货，总库存待确认（unverified） | 保留到货事实；账面总量标为未知，旧实盘历史保留 |
| 实购量或单位未知，或没有明确 SKU 的临时商品 | 「到着だけを確認（在庫には未反映）」 | 仅物流到货确认，不增加库存，不生成虚假的库存流水 |

后两种不是“库存为零”，也不代表能准确恢复销售。待负责人补齐信息或员工真实清点后再判断。

**防止重复加库存的例子：** 原有 10 个，新到 2 袋，每袋 20 个。如果未计入新货就登记 add，变为 50 个；如果已经把新旧一起清点为 50 个，补登记这 2 袋必须选 included，仍为 50 个。首次不知道旧库存时，先将新旧一起实盘，再关联已包含到货，不能假设旧库存为零。

**不同进口包装的例子：** 旧批每袋 20 个，剩半袋就是 10 个；新批每袋 30 个，到 1 袋就是 30 个，合计 40 个。不能把旧半袋按今天的 30 个规格改算成 15 个；混合库存按“个”清点。

发送后结果未知时，保留原商品、数量、位置和同一操作，使用「同じ内容で再送」。验证过期就验证原操作人后重试；不要重新建一笔不同内容的入库。冲突时核对刷新后的事实，再作明确调整。

入库完成后还要检查库存是否足够、质量报告是否解决、菜单是否恢复，以及各平台的恢复结果。当前不会因成功入库自动恢复所有平台。库存登记后的错误、退货或冲销交管理人员处理，当前没有完整员工冲销流程，不能直接改旧购买量或再登记一笔虚假的“入库”来修正。

## 底料预制品与加盟供给

底料、预制品和向加盟店供给的商品都使用独立 SKU；不要求它必须直接作为顾客菜单出售。

制造时使用制造配方：投入原料、登记本次实际产量、选择成品库位。实际投入有计量才能准确扣原料；只是标准目安时保留预计耗用，不能假装已测量。

例：实际投入原料 3 kg、实际产出底料 10 kg，记录原料减少及底料增加。顾客菜单每份使用底料 0.1 kg 时，订单只扣底料 SKU，不能再把制作底料用过的原料重复扣一次。

门店间供给在来源店发出后扣来源库存，目标店只显示在途；目标店实际收到后才增加库存。发出 8 kg、先收到 5 kg，剩余 3 kg 仍在途或待核对，不自动补齐。短收、损坏、运输报损须有对应处理记录，不能伪造成全收。

这些功能目前使用 OS 的制造和门店转移入口；Store 员工的备料、发出和接收执行页待补。加盟店只能查看其获授权的商品及必要信息，成本和供货价分别记录；移库本身不等于付款。

## 定期清点与智能预测

负责人安排重点 SKU 定期实盘，其余按风险轮换检查；不要求所有员工每天把全部食材精确数一遍。

无待制作占用时，例：清点起点 10 个，实际入库 40 个，已制作准确耗用 35 个，理论实物剩 15 个；实际清点 13 个，差异为 −2 个。显示“差异待核查”，不能自动叫作损耗。原因可能是漏记、替代、包装误差、报损或制作偏差。

接单新流程存在占用时，须先还原理论实物再与实盘比较。例如可售 14 个、待制作已扣 1 个，理论实物仍是 15 个；实盘 15 个，没有数量差异。接单占用、取消释放、制造和调拨必须分别识别，取消释放不能算采购入库。

没有固定用量的原料，可以通过两次真实清点、期间实际入库和已制作份数学习平均耗用；接单需求用于预计需求，但尚未制作的订单不算实际消耗。粗略巡查不训练精确模型。单位变化、未映射订单、未知入库或未计量制造存在时，显示预测依据不完整，不保证精确耗尽日期，也不单凭预测自动停售。

现有差异与预测功能按制作时点实现；改为接单扣减时必须一并调整上述计算，否则会把待制作占用误认成损耗。

## 审查发现与优化优先级

P0 表示接单即时扣减或扩大员工操作前必须解决；P1 表示直接影响日常衔接、正确性和效率；P2 表示后续增强。下列为本轮代码与流程审查发现，未进行线上业务写入复现。

| 优先级 | 不合理或未完成之处 | 要改的结果 |
| --- | --- | --- |
| P0 | 现有逻辑仍到制作时才扣，与接单即扣决定不符；缺少未制作占用及取消释放 | 冻结有效接单时点和准确用量，接单扣可售、制作不二扣、未制作取消按明细幂等释放 |
| P0 | 当前清点把账面直接重置为实盘；接单后中途清点会把占用恢复为可售；预测也按旧耗用口径 | 保留实物、待制作占用、可售三类数量；清点保留占用；差异和学习使用实际耗用 |
| P0 | 三平台导入只有完整详情采集才形成 OS 订单，身份仍不可信；不足一份也未触发菜单停售 | 完善原单、菜单与选项的可靠映射和接收及时性；按完整配方可制作份数阻挡，与扣减同事务持久化停售任务，逐平台确认及重试 |
| P0 | 人工恢复会清直接目标多个阻挡原因；新自动停售不能沿用这种清法 | 使用独立 SKU 缺货原因；补货或取消只解除该原因，质量、人工及其他原料阻挡保留 |
| P0 | 部分采购写 API 只检查可写会话和门店范围，页面模块权限与 API 权限不完全一致 | 请求、购买、到货和调整各自检查实际权限与范围，不能靠隐藏页面来控制写入 |
| P1 | Web 菜单“强制可售”可优先于整体缺货；当前提交另检查整体状态，可能显示可买却提交被拒 | 列表、下单及平台同步统一使用缺货硬阻挡优先的规则；不声称已经证明缺货成交 |
| P1 | 桌台请求里的缺货或不存在选项可能先被过滤，顾客选择静默消失 | 校验全部原始选项 ID 与数量，缺货时明确拒绝并要求重新选择 |
| P1 | 员工能清点、收货，Store 却没有补货申请入口；通知还可能指向无权打开的 OS 发注页 | Store 增加补货请求及进度入口；通知按收件人权限指向可执行页面 |
| P1 | 风险列表不是持久需求池；没有负责人、建议量、在途抵扣及满足记录 | 一店一 SKU 合并开放需求，采购进度与库存风险分开，按有效在途和包装计算建议量 |
| P1 | 补货读取只含不足库位，无法得出全店可用量；正常库位可能有货 | 同时读取相关正常、隔离及未知库位，明确换算和可用范围，先内部补位再采购 |
| P1 | 主单位为袋、本批按箱购买时，合法全部入库仍可能被补货列表误报未入库 | 复用历史本批包装及分单位累计入库判断，不能与今天商品主单位简单比较 |
| P1 | “已清点包含”主要依赖员工判断；入库文案又容易让人误以为必须再单独门店确认 | 提问“最近清点是否包含这批货”，显示清点时间与明细；清楚展示一次提交保存的结果 |
| P1 | 到货状态先提交、通知后发送，失败重试可能漏通知；时间窗口去重可能吞新到货或重复发送 | 业务事件与通知待发送记录同事务，按事件及收件人去重；通知失败可恢复 |
| P1 | 同订单同发注先再次上传收据会替换当前引用，多次购买没有独立完整收据历史 | 按真实履行分别保存购买、到货与多份レシート，保留旧凭证引用 |
| P1 | 入库后退货、纠正、短收和报损没有完整员工闭环 | 新增明确纠正流水和处理责任，保留原始采购、入库及实盘，不直接改历史或伪造加减 |
| P2 | 制造、备料、调拨实际在店里做，但员工还需依赖 OS 管理人员执行 | 增加 Store 执行入口；配方、价格、SKU 与规则继续由 OS 维护 |
| P2 | 本次包装确认、逐明细入库和整数购买限制增加输入负担 | 常用包装预选、批量确认正常项、只展开异常项；按供应商和 SKU 定义整数或可分量购买 |

### 实施顺序与验收例子

1. 先完成订单接收身份与冻结明细、接单扣可售、取消释放、清点保留占用及现有 API 权限一致性。
2. 接通库存硬阻挡、逐平台停售和恢复结果；自有菜单与下单校验采用同一有效可售判断。
3. 增加 Store 补货请求，升级合并需求池；同时修正进口包装未入库误报、通知入口和建议采购量。
4. 简化收货确认，完善纠正及短收流程，再下移 Store 制造、备料与调拨执行。

验收至少包含：最后一个芋头在不同平台并发下单、同一原单重复导入、接单后尚未制作就清点、未制作取消和已制作退款、重复网络入库、先实盘后补登记到货、两种进口包装混用、购买不可仍缺货、某个平台同步失败，以及员工与总部权限拒绝。

## 员工当前操作速查

| 场景 | 当前操作 |
| --- | --- |
| 开班或交班巡查 | Store 在庫確認，先看关键食材与不足，普通项目粗略确认 |
| 要准确知道剩多少 | 数量で棚卸，填实物与正确单位 |
| 最后一份被订单占用 | 立即通知负责人设置菜单缺货，负责人核对各平台同步；不假填实盘 0 |
| 发现缺货 | 保存对应报告；店长统一核对补货，不逐次另建采购 |
| 发现质量问题 | 保存质量报告，立即通知有权限负责人判断隔离及停售，再核对补货 |
| 有货到了 | Store 納品・入庫，核对明细、实到量、位置和本批包装 |
| 刚才已把新货一起清点 | 选择清点已包含，只登记到货对应 |
| 数量或包装不确定 | 使用适用的待确认方式，交负责人补信息；不把未知填零 |
| 发送结果不明或验证过期 | 保留原操作，同一员工验证后使用同一内容重试 |
| 到货后准备恢复销售 | 负责人确认库存及其他停售原因，再恢复并核对各平台结果 |
