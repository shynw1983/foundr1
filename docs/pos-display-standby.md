# Configurable customer-display standby

The Store customer display reuses a store-owned visual layout configured in `/os/pos` → **客席表示** → **待機画面を編集**. Existing stores remain unchanged until **この待機画面を使う** is enabled and saved. The designer supports clock/date, text, image/logo and store-name blocks; positions and dimensions use percentages. Portrait and landscape are independent layouts, selected from the actual viewport. The editor and live display use `PosDisplayStandbyCanvas`; the same geometry, color, font sizing and content render in both.

The default draft places the clock at the top left, a blank logo area at the top right, welcome text in the center and the store name below. The blank logo is only an editor placeholder. Staff can add/delete blocks, drag or move with arrow keys, and edit numeric geometry. Numeric input commits on blur or Enter so replacing a number does not clamp an intermediate empty string. Customer-authored copy is excluded from automatic OS UI translation.

The editor's **グリッドに吸着** starts enabled. Dragging aligns to the visible 5% grid; approaching the canvas center takes priority even when a block's exact center is between grid lines. Switching snapping off permits tenth-percent placement. Clicking a block or dragging on one axis does not snap its untouched coordinate. Arrow keys (1%, Shift: 5%) and numeric fields remain exact fine adjustments regardless of the toggle. The toggle is an editor aid and does not modify saved settings.

Selecting a block shows dashed center guides; each guide turns solid green when that axis is centered. The **左右中央** and **上下中央** indicators show a check when aligned. **左右中央に配置** and **上下中央に配置** center the block's bounding box independently, without changing its size, text alignment or the other orientation's layout. Grid and guides are editor-only and never appear on the customer screen.

Configuration lives in the existing `pos_store_settings.customer_display_media_settings.standby` JSON. No database migration is needed. Dedicated `section: customerDisplayStandby` saves only that key, leaving prices, printing, tax, discount, scale, existing ads and unknown future fields intact. New full saves opt in using top-level `customerDisplayStandby`; stale nested standby fields in old clients cannot overwrite the designer. Both existing scope checks and `pos.manageSettings` apply. Store changes and unsaved edits use the existing OS guard.

Image uploads reuse the existing private customer-display media upload and public image-serving path. URLs must be HTTPS or same-origin relative paths; data/script/SVG URLs are rejected. Upload completion is scoped to its original store and block. The editor aborts uploads on unmount/store change; all settings saves are blocked while upload is pending so a stale save response cannot erase the new image. Uploads alone do not activate or save a layout.

When enabled, the layout replaces idle/advertising only while the display has no items, active weighing or scanner. Cart, payment, change, membership and completion keep the current renderer. Configured slideshow/video data is retained and resumes when the custom layout is disabled. A display can read saved changes through its menu's **更新** action; the editor shows that instruction after saving. The POS debug display uses the same layout with its persistent test label and independent transient connection.

## Gesture containment

`useCustomerDisplayGuard` scopes horizontal overscroll containment to the mounted display. A non-passive listener cancels single-finger starts in the 24px screen edge when the target is noninteractive display content. Buttons, links, form controls, center vertical scrolling and pinch zoom remain usable. The menu has an explicit confirmed exit. No history entries, popstate traps, persistent browser state or beforeunload warnings are added. Styles and listeners are removed on unmount, including overlapping mounts.

This is best-effort browser behavior; JavaScript cannot guarantee control of Safari's system back gesture. WebKit tracks relevant limitations in [240183](https://bugs.webkit.org/show_bug.cgi?id=240183); [248303](https://bugs.webkit.org/show_bug.cgi?id=248303) explains why script-created history is not a reliable back-swipe trap. For an unattended iPhone display, [Apple Guided Access](https://support.apple.com/111795) can disable touch for the app session. Guided Access without disabling touch does not itself disable navigation inside Safari. No native Android capability or APK is changed by this patch.

## Verification boundary

Use isolated PostgreSQL/API checks for permissions, payload validation, exact JSON preservation and absent business side effects. Browser tests exercise the actual editor and renderer at phone/tablet/desktop sizes, draft preservation, image upload/save ordering, manual reload and active checkout transitions. Edge-event and actual Chromium vertical-scroll checks validate the web handlers; they do not prove Safari's OS gesture behavior. Real iPhone/Safari and deployed realtime behavior require separate field verification.

The brand websites, menus, live store configuration and receipt templates are unchanged. This implementation extends the published POS debug and standby package; source/release evidence must distinguish this landscape update from its publication.

## Phone landscape (2026-10-21)

The phone's available height, not width alone, determines the compact customer-display layout. Short landscape screens keep order details on the left and payment information on the right. The large built-in clock is omitted in this layout so the total, received cash and change have priority. A long order scrolls inside its own list; it must not push the payment values below the screen. Normal and debug display states use the same layout boundary, and the debug indicator remains visible.

The editor can preview a landscape layout at phone, tablet and wide-screen proportions. Changing the preview device only changes the editor's presentation; it must not mutate any stored block or mark the layout as edited. Existing portrait and landscape content remains store-owned. In particular, a clock that the manager placed in a custom standby layout is retained and can be deleted with the existing block control.

Verification includes iPhone 11-sized 896×414 and reduced-height 896×340 / 808×320 viewports, plus portrait, tablet and desktop regressions. Viewport simulation is not a physical iPhone Safari test. The change requires no migration, native update, menu update or automatic store-configuration save.

## Per-block fonts (2026-10-21)

Text, store-name and clock blocks each have a **フォント** choice: **シンプル（標準）** or **クラシック（Georgia）**. Portrait and landscape choices are independent, using the existing store-owned standby JSON and save action. Missing font fields in existing saved layouts normalize to `standard`, preserving their current appearance and enabled state. Only the two enum values are accepted; arbitrary font names or CSS are rejected.

The editor and customer display share the same renderer. Classic text uses the original `Georgia, "Times New Roman", serif` stack; classic clock digits also use the original weight 400, while the date remains in the inherited system font. Standard fonts retain the existing inherited appearance. Font availability follows the device's installed faces and the same fallback stack as the original display; this does not download or install a font. Images have no font control. Settings become visible on the customer display after its existing **更新** action or a reload.

## Optional comfort widgets (2026-10-21)

Managers can explicitly add a standalone **日付**, **天気**, **ことばの雲**, or rotating **メッセージ** block. These do not appear in existing layouts automatically. Date uses Asia/Tokyo and has a year toggle, independent of the clock. Font, color, size and geometry continue to be per block and per orientation.

The welcome cloud accepts one authored phrase per line (up to 12 lines, 80 Unicode code points per line, 500 code units total). Its preset contains Japanese, English, Simplified/Traditional Chinese, Korean, Vietnamese and Nepali welcomes; it is editable store copy, not menu/catalog translation. A seeded scatter arrangement keeps phrase positions consistent in preview and live display. Automatic size variation is enabled by default, with explicit per-phrase sizes taking priority. Motion uses a horizontally repeating plane moving from left to right, rather than rows that wait empty between turns. The configured time is the time to advance one screen width; repeats remain continuous across screen edges. Rotating messages use the same bounded lines, showing one phrase at a time. Motion can be stopped, intervals are bounded to 8–90 seconds, and reduced-motion/hidden-page settings pause animation. No generated fortune, commercial claim, waiting-time estimate or customer tracking is introduced.

Weather uses the store's saved weather coordinates (or a complete attendance-coordinate pair) through the existing forecast service and a scope-protected GET endpoint. It does not request customer-device geolocation or accept client coordinates. The block is explicitly a daily forecast for the current JST day. **天気の表示** selects **詳しく表示** (forecast heading, condition and high/low temperatures) or **アイコンのみ** (the condition icon without those text details). Both modes retain the component's existing position, size and color controls. The optional weather-only field `weatherDisplay?: 'details' | 'icon'` accepts explicit enum values only. Missing historical values render as detailed weather and remain absent during normalization; the field is emitted only for weather blocks when explicitly supplied. Changing the selector updates the editor preview immediately and requires the existing save action to affect the customer display. The customer-facing weather block has no provider footer at rest. Tapping its condition icon opens forecast details with the source link and applicable license attribution; the editor describes this interaction without making the component-selection preview interactive. Forecast source metadata remains available in the protected weather response. Fetches are deduplicated and refreshed at most every 30 minutes while visible; failures retry with a bounded delay. A retained forecast is labelled as awaiting refresh, and yesterday's forecast is never shown as today's after midnight. Missing settings or unavailable data show a quiet neutral placeholder. Coordinates and the store's full address are not sent to the browser or saved by this feature.

Components exist only inside standby. An active cart/weighing/payment/scanner continues to use the operational customer display. Existing slideshow/video, menus, prices, print data and transactions retain their current flow.


## Full-width welcome scrolling and phrase sizes (2026-10-21)

The welcome cloud uses full-screen left-to-right travel in **左から右に流す** mode. Its saved x/width remain intact, but the effective motion band is x=0 / width=100%; the editor shows these values and disables horizontal positioning/centering. The saved y and height set the vertical band. **静止** uses the saved rectangle and a compact static arrangement. Reduced-motion settings and pausing the selected component keep the full-width band in scrolling mode and show a static overview; **流れる動きをプレビュー** plays the actual crossing and actual requested text sizes. The editor-only playback choice resets on store, selection, orientation, preview-device and motion changes and is never saved. Changing a flow slider or applying the soft-flow preset starts the preview when the block is in scrolling mode. The pause control remains available; adjusting individual sliders never overrides **静止** or reduced-motion preferences. The explicit soft-flow preset selects scrolling mode; reduced-motion preferences still apply.

The base font-size field controls the overall scale. **文字サイズの差** replaces the former automatic-size checkbox: 0 uses the base size for unmodified phrases, and increasing the slider spreads automatic sizes further apart. The **1行ごとの文字サイズ** controls allow each trimmed, nonempty phrase to use a separate 2–20 size in the same shorter-canvas-side units as the base font size. **すべて基本サイズに揃える** removes all overrides, switches to uniform sizes and sets contrast to 0, so later base-size changes affect every phrase. Moving text preserves the requested size without shrinking to the text width; the static overview may fit an impossible layout into its cells.

`wordFontSizes?: (number | null)[]` is stored only on word-cloud blocks. Missing fields stay missing during normalization; null or a missing entry uses the shared automatic/uniform size calculation. Explicit arrays are bounded to 12 entries and no more entries than nonempty phrases, with only null or finite numbers in 2–20 accepted. Textarea edits match trimmed phrases by occurrence, so reordering retains their explicit sizes, deleted phrases lose their override and new or changed phrases use the selected automatic/uniform mode. Existing 500-code-unit, 12-line and 80-Unicode-code-point limits still apply. Existing cloud geometry and store-authored copy are not migrated or saved automatically.


## Dense welcome arrangement and automatic size variation (2026-10-21)

`wordSizeMode?: 'varied' | 'uniform'` is an optional word-cloud field. Missing values render as `varied`, while normalization leaves absent fields absent; only explicit valid enum values are accepted and only word-cloud blocks output the field. Existing saved base sizes and rectangles remain unchanged, and new clouds keep the base size 7. This rollout does not automatically save store configuration.

The pure `getPosDisplayStandbyWordFontSize(block, index)` function is shared by inspector and renderer. A valid explicit phrase size always wins. Uniform mode uses the base. Varied mode ranks seeded phrase identities and applies `1 - 0.7*c + rank/(n-1)*c`, where `c=(wordSizeContrast ?? 50)/100`. Results round to half units and remain bounded to 2–20. At the historical default contrast 50, factors remain evenly spread from 0.65 to 1.15 of the base. A single phrase uses the base. The renderer does not apply a second random shrink to these values. Each phrase field shows its effective size and whether it comes from automatic variation, the base or an explicit override.

**画面幅ぶん進む時間（秒）** sets the time for the scrolling plane to move one screen width, independent of phrase length. The repeat arrangement fills the plane with staggered horizontal and vertical offsets, preserving a steady left-to-right flow. Static and reduced-motion settings retain the existing no-animation behavior.

## Adjustable welcome flow (2026-10-21)

The editor groups four compact, keyboard-accessible sliders under **ことばの流れ**, with current numerical values and plain endpoint labels. **文字の密度** adjusts the intended amount from 50–180% (historical default 100); actual capacity depends on phrase widths, requested sizes and the selected vertical band. **文字サイズの差** ranges from 0–100% (historical default 50), while manual phrase sizes always take priority. **画面幅ぶん進む時間（秒）** remains 8–90 seconds, with larger values moving more slowly. **速度の差** is 0–40% (historical default 0), adding a restrained difference between flowing layers rather than abrupt random acceleration. Its zero value retains the previous shared-speed behavior. Motion remains rightward and continuous; text must not collide as the layers pass. If large text in a narrow vertical band cannot fit two safe corridors, the renderer retains a shared speed. The editor explains this space limit whenever the speed-variance control is above 0.

The optional cloud-only numeric fields are `wordDensity`, `wordSizeContrast` and `wordSpeedVariance`. Validation accepts finite numbers only and rejects explicit nulls, numeric strings and values outside their ranges. Absent historical fields stay absent when normalizing and saving an untouched layout; their defaults apply only while rendering and editing. Valid numeric fields on a non-cloud block are not persisted. Contrast slider 0 explicitly selects `wordSizeMode: 'uniform'`; a positive slider value selects `'varied'`.

**やわらかい流れに整える** applies density 115, contrast 65, speed variance 18 and a 32-second screen-width travel time, selecting varied sizing so the contrast is visible and scrolling mode so the flow can be previewed immediately. It preserves existing explicit phrase sizes, text, font, color and geometry. It does not save store settings. In landscape cloud editing, a compact, aspect-correct sticky preview stays beside or above the controls and the longer placement guidance is collapsed. Preview-device selection, slider playback and pause state remain editor-only; only **待機画面を保存** publishes the authored settings to the store's customer display. Active orders, menu data, transactions, printing and scale flows are unaffected.

## Temporarily hiding individual blocks

Select a block and turn off **この部品を表示**. The editor selector marks it **非表示** so it can still be selected, edited and restored. Both the editor canvas and the customer canvas omit the block entirely while hidden; its text, image, geometry, fonts and animation settings remain saved. Hidden weather blocks do not enable weather polling. Portrait and landscape visibility are independent. Hidden blocks still count toward the existing16-block layout limit; an empty visible layout intentionally shows only the configured background.

The optional boolean `hidden` is stored on each block inside the existing standby JSON. Missing values preserve existing visible behavior; explicitly invalid values are rejected. No schema migration, automatic setting activation or Android update is involved. Save the standby layout and refresh the customer display through its existing menu to apply the change. Order, weighing and payment content outside the idle layout are unaffected.
