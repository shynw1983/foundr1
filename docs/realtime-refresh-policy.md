# 实时更新、轮询与恢复统一规范

状态：2026-11-03 确认的系统开发要求。适用于 OS、Store、POS、客显、品牌网站相关读模型，以及 Android / Desktop Bridge 的同步链路。它定义后续新增和改造的要求，不表示现有模块已完成改造。当前差异见[本轮排查记录](realtime-refresh-audit-20261103.md)。

## 1. 统一原则

**推送优先，权威读取确认；健康时低频核对，订阅不可用时兜底；按业务时效保留必要例外。**

不得统一为仅在 WebSocket 断线时才查询。数据库提交后发布失败、订阅窗口内漏消息、读取途中到达新事件，都可能发生在客户端仍显示连接正常时。当前实现并无覆盖所有模块的持久化事件重放与缺口补偿，因此不能把连接正常视作数据必然完整。

统一的是机制、健康状态、资源作用域和验收规则，不要求所有功能使用同一个间隔。禁止为了补一个漏刷问题，直接增加不区分连接状态的高频常驻轮询。

## 2. 必须区分的请求与定时器

| 类别 | 用途与要求 |
| --- | --- |
| 推送触发读取 | 事件作为状态失效提示，合并后读取有门店、身份和权限校验的 API；有完整版本控制的可信快照可按其契约应用 |
| 健康时一致性核对 | 修复连接正常但漏消息、发布失败等情况；优先读取轻量版本号、游标或变更摘要，不反复下载整个目录 |
| 订阅不可用兜底 | 在未订阅、订阅失败、断开、重连中等状态下维持状态可见性 |
| 活动任务状态确认 | 仅在明确任务执行中跟踪进度、完成或超时，任务终态后退出快节奏 |
| 心跳、租约续期、协议 ping/pong | 证明设备存活、维持已授权操作权或检测传输故障；按协议有效期执行，与列表刷新分开 |
| 采样、有效期校验、本地 UI timer | 电子秤采样、旧读数失效检查、时钟和动画等；本地每秒执行不等于每秒发 HTTP |
| 外部数据与临时握手 | 天气等按来源缓存有效期；二维码授权、支付结果确认等按有限会话和服务端协议执行，不能拿无关 Pusher 连接代替 |

没有对应业务推送源、完整事件覆盖或可用订阅健康信号的模块，不得借用全局 connected 标记直接停查。先补齐链路，或保留有界读取并登记原因。

## 3. 默认读取档位

以下是**目标基础间隔**，不是当前线上频率，也不是保证送达时限。具体最大陈旧时间必须覆盖请求耗时、抖动、失败与恢复；超过它应显示过期/离线，必要时暂停依赖新鲜状态的操作。

| 业务档位 | 订阅健康时 | 订阅不可用但 HTTP 可用时 |
| --- | --- | --- |
| 本日统计等一般展示读模型 | 事件驱动＋5 分钟轻量核对 | 60 秒起步补查 |
| 订单、厨房、叫号、出餐、总部操作提醒等时效重要状态 | 事件驱动＋60 秒轻量核对 | 30 秒起步补查；必须按该业务允许延迟核定上限 |
| 非紧急主题、装饰和低时效信息 | 已有完整推送源时事件驱动＋15 分钟轻量核对；没有时可按同档查询 | 默认 5 分钟补查，明确打开页面可立即读取 |
| 执行中的同步、打印等任务进度 | 事件优先；事件不足时只跟踪当前任务，默认 5–10 秒有界确认 | 按任务协议确认到终态或超时；不能无限显示执行中 |
| 活跃称重、客显称重预览、设备心跳、收银操作权 | 沿独立的采样、新鲜度、心跳和租约契约 | 不受普通页面 Pusher 开关控制，不能直接套用上表慢速间隔 |
| 人工发布的菜单、价格与编辑草稿 | 保留人工更新/应用规则 | 不得借兜底、重连或切回前台自动替换菜单、价格或草稿 |

低频核对读取状态而非重做业务。比如打印列表的读取不等于打印，菜单同步进度读取不等于重新发起同步。

短于默认间隔、需要后台持续运行、或取消健康核对时，必须记录模块、资源范围、原因、有效状态、最大陈旧时间、停止条件、恢复路径和验证证据。标准档位内的例行选择不新增用户审批；既有用户决定与具体业务安全契约优先。

完全取消健康核对，须先证明端到端的持久化投递/等效保障、版本或游标缺口检测、重放与重连补偿能覆盖最大陈旧时间。仅增加服务端 outbox，或仅看到 Pusher 订阅成功，均不满足此条件。

## 4. 订阅健康与恢复

- 健康必须对应当前账号、门店、资源，以及该读模型所需的全部已授权频道。单个 socket connected、任一频道成功，不能代表所有功能均健康。
- 统一区分 connecting、subscribed、degraded/reconnecting、unavailable、unauthorized 等实际业务状态。订阅失败、部分频道失败、订阅超时和认证失效必须可见，不能只监听 disconnected。
- 首次进入、必要频道订阅成功/重新订阅成功、网络恢复、页面恢复可见时，补读权威快照；新事件只做增量更新的模块也必须补齐断线期间的数据。相邻的 focus/pageshow/visible/online 唤醒应合并，不应同一刻重复请求。
- 避免先取快照、后订阅之间的空窗：订阅成功后再次校准，或使用等效游标机制。
- 401/403 不属于普通离线。停止相关未授权订阅和自动重试，处理重新认证/权限恢复，隔离或清理敏感视图与缓存；禁止改用匿名或更高权限身份兜底。
- 推送不是权限凭证。读取、写入、领取任务、ACK、续期等仍须逐次核验服务端身份、门店范围和该操作所需权限。

## 5. 并发、退避与页面生命周期

- 同一页面或客户端运行实例内，同一身份/门店/资源只有一个刷新协调器和一个在途读取。推送、周期核对、断线补查和人工刷新共用它；不能为同一接口叠加互不知情的多个 timer。不同设备或独立会话仍各自校准，不引入跨设备的全局主从选举；写操作的独占权仍由原有租约协议控制。
- **去重不能吞掉新事件。** 读取途中发生变更，必须记录 dirty/readAgain，当前请求结束后再补读一次，或使用等效版本/游标机制。直接返回旧 Promise 或 inFlight return 不足以证明已消费该事件。
- 旧账号、旧门店、已卸载页面、较旧 revision，以及晚于新结账/退款快照到达的旧响应，不得覆盖新状态。失败不应把未知状态伪装成零订单、无待办或成功。
- 明确区分真正的订阅中断时长、HTTP 连续失败次数、最后成功校准时间和活动任务持续时间。不得把 poller 从 start 起的运行时长当作断线时长，亦不得让健康时核对被无关断线退避拉长。
- HTTP 超时、429、5xx 等才进入相应失败策略；遵守 Retry-After，使用有上限的指数退避与抖动。成功/恢复后复位。不能 catch 后当成功返回，导致调度器永远看不到失败；取消的旧请求与切换作用域不计作网络失败。
- 普通页面隐藏、退出或空闲时暂停/降频，恢复可见先校准。关店判断优先使用服务端实际营业/值班/收银状态；不能仅因超过计划营业时间，就停止未完成订单、运行任务或仍需续期的合法设备协议。页面隐藏时需要暂停/释放收银操作权的，仍沿该设备契约执行，恢复前先核验；本规范不授权强行保活或长期占用收银台。
- 自动刷新不得抢焦点、打开面板、清空购物车、替换人工菜单、重置输入、重复播报。保留人工刷新入口和非阻塞的失败/过期提示。

## 6. 必须保留的安全边界

- 操作权续期、设备心跳、数据新鲜度由各自 TTL 决定，须留足往返与失败恢复余量。不得为了减少请求而顺手延长租期、删除超时、放宽称重稳定/时效或绕过 epoch、序号、去皮和配置版本检查。
- 活跃称重按真实测量时间与有序采样验证；收到 HTTP 或推送的时间不能把旧重量重新变新。退出称重、关店、后台释放后，不能继续接受过期或旧会话读数。
- 网络未知结果不等于业务失败，更不等于可重新执行。支付、结账、退款、库存写入、同步命令和打印保留原操作身份、幂等、领取锁及 ACK/超时机制；恢复连接先核对已有结果。
- 推送到达/连接成功/列表刷新不能直接造成再次收款、自动重打、重建订单、重复扣库存或重新发起同步。打印 sending/uncertain 不能因轮询超时就自动当作成功或重发实体打印。对已持久化且已授权的命令，推送可以唤醒正常认证领取与执行流程，但必须保留幂等和 ACK，不能因重复事件生成第二条业务命令。
- 通知收到、实际展示、员工已读和问题解决是不同状态；不得用查询成功或 Pusher 在线自动填写已读。可见性检查可能只是本地 timer，不能误作网络轮询删掉。

## 7. 开发与验收要求

新增或修改后台刷新，必须先沿写入端、事件发布端、私有频道授权、读取端和副作用消费者核对完整链路，选择并记录上述档位。Store 网络读取优先复用/完善共享调度机制；现有 helper 不具备订阅健康或 trailing refresh 时先补足能力，不得假设它已经符合本规范。

行为改造须验证：

1. 健康推送立即更新，健康但丢失一条事件/发布失败时在规定核对时间内恢复。
2. 断线、部分订阅失败、订阅超时、重连、后台挂起与重新可见均能恢复；重连期间的变化不会永久漏掉。
3. 新事件在读取途中到达会补读；旧响应、重复/乱序事件、账号/门店切换不会倒退或串店。
4. 按实际 HTTP 请求数验证健康、断线、任务执行、空闲、隐藏和关店时的请求预算；时钟/动画/本地检查不计作 HTTP。
5. 401/403、HTTP 超时/429/5xx、真实退避复位、跨店访问拒绝，以及数据过期阻断按其模块执行。
6. 打印/结账/退款/库存与通知的幂等、ACK、人工确认、租约和采样有效期不因降频退化。硬件或运行时是否实际安装另行核实，代码/发布检查不替代实机验收。

普通读取的新机制应在测试中断网、丢推送、制造在途竞态并检查请求次数后再调整频率。禁止先删 timer，再以正常网络下能刷新作为恢复能力证明。

## 8. 现存模块的处理

最初排查轮次只写入规则，未改动运行时。随后经用户授权进行的 Web 改造范围、档位、例外及验证边界见[2026-11-03 改造记录](realtime-refresh-rollout-20261103.md)，正式发布状态以该记录所指的发布证据为准。未覆盖的原生运行时和历史模块不能据此认定已完成迁移。以后新增/修改刷新逻辑时必须遵守本规范；无关的小改不要求顺带重构全系统。

改造顺序：先补齐订阅健康、重连校准、事件在途补读和缺失的发布链路；再合并重复调度、验证恢复及业务副作用；最后按档位降频并分别报告代码、服务端发布、原生安装与实机结果。

### POS completed-sale print notice

The completed-sale notice consumes the existing print queue coordinator, scoped to the exact paid order. It does not create another timer, retry a print, or interpret an empty/partial queue as success. A terminal message requires a complete order-scoped document set; uncertain/read failures remain reviewable. Amount, discount and change remain visible while only the status label changes.
