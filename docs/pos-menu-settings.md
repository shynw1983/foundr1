# Physical-store POS menu configuration

Decision and local implementation: 2026-10-16, with independent dine-in menu development approved on 2026-10-20. No live menu, price, migration or deployment is implied by this document.

The operator retained the existing 50g specifications for toppings such as beef tendon and pork cartilage. The original 2026-10-16 implementation supplied configuration without choosing a retained assortment or new prices. The 2026-10-20 independent menu copies the effective configuration that exists when initialized; it does not guess a new assortment, rename portions or reprice existing products.

The 2026-10-17 clarification places separately charged premium ingredient assembly in the kitchen. Cashiers record the chosen portions and surcharges per bowl; kitchen and finishing tickets carry those choices. Premium ingredients are not added to the weighed bowl at the register. This clarification does not choose menu records, enable groups or set store prices.

## Ownership and scope

- Menu management has one brand selector at the top of `/os/menus`. It controls item/category/option editing, translation, availability links, POS settings and external publication together. This browser remembers the selected brand separately for each global store context; inactive/deleted brands fall back to a currently available brand. Switching or restoring the selection only reads menu data and never saves business configuration.
- Brand master IDs, names, translations, photos, portions and item/group links continue to supply websites, Web予約 and external delivery menus. The independent dine-in catalog described below owns its own customer labels and stable local identities. It is still OS menu data, rather than a catalog hard-coded into a frontend.
- `/os/menus` → `共通 POS メニュー設定` selects a store and brand, then an item, group or option. Visibility is inherit/show/hide. Hide is independent of stockout. A hidden parent group also hides its children. Explicit show never overrides a genuine stockout or inactive master record.
- Items and options can inherit brand prices or have a non-negative integer POS price, including zero. Group prices are not accepted. Unconfigured items preserve identified existing legacy POS behavior; an explicitly saved item using inherited pricing follows `base_price`, rather than a shared legacy store-price override. Weighted item amounts still use the existing store's gram price; option overrides charge per selection of the existing portion.
- A group explicitly shown in store configuration becomes eligible for the existing weighed-bowl selection flow, including premium/VIP groups. Selection limits, item applicability and required-group rules remain the brand's rules. Hiding the whole group deliberately removes it from that POS flow; hiding every option of a required visible group is rejected.
- The original visibility/price settings affect `/api/store/pos`, including counter takeout under the existing pricing rules. The independent catalog below is restricted to POS `eat_in`; it does not replace the counter-takeout catalog. Web予約, public menus, table-order placement/settlement and external delivery publication continue reading the original master and their existing configuration. Neither brand website needs a frontend change because its public API contract and prices are unchanged.
- Uber source synchronization continues updating the brand master and identified legacy shared overrides. It does not write the separate `menu_pos_settings` table. Explicit POS prices survive brand price changes; inherited prices follow the master.

## Authorization and consistency

The new management API `/api/os/menus/pos-settings` checks active employee authentication, `menus.edit`, explicit active-store scope and store-brand membership. Each target must belong to that brand. POST requires same-origin requests, strict visibility/price types and a revision from the prior read. No new staff or terminal management permission is granted.

The store configuration has an aggregate revision. Saves use a store advisory transaction lock and revision guard to reject concurrent stale edits. POS GET returns this revision; checkout rejects stale or pre-feature clients once a store has configuration. The checkout transaction acquires the same lock and rechecks the revision, preventing a price/visibility change between validation and persistence. Saved-order recovery runs before current configuration checks and retains its original transaction, amount and ticket codes. Old offline queues cannot silently adopt a changed POS configuration; reconcile them before activating a store.

Order items retain the original menu/option IDs and actual charged price snapshot. Kitchen, three-ticket relay/direct printing, customer display and receipts consume the same validated order data. Existing display/receipt translation ownership remains unchanged.

## Migration and rollout

`db/migrations/20261016_pos_menu_settings.sql` is additive, with foreign keys, single-target checks and separate uniqueness constraints for item/group/option settings. It creates no configuration rows. Maintain `db/schema.sql` and `scripts/check-db.mjs` with it. Missing-table handling preserves existing POS behavior while the new editor reports migration required; other database failures do not silently bypass configuration.

Before activation: review retained groups/options and store prices, drain or reconcile offline queues, apply the migration to the authorized database, deploy the runtime and refresh POS clients. Saving settings does not publish to delivery or change stock. No live settings are applied by this task without separate authorization.

## Independent dine-in menu (2026-10-20)

The first intended store is 桜並木店. The capability is keyed by store and brand, and remains absent for every store until an authorized manager explicitly initializes it. The existing menu-management brand selector and its saved browser selection also govern the dine-in editor. Switching brand or store only reads data; it never creates a menu or saves an in-progress edit.

Initialization offers an empty menu or an explicit copy of the store's current effective POS menu. An empty menu defaults to disabled: creating and editing the draft does not replace the running POS menu until a manager enables it. Existing initialized menus are retained. A copied menu preserves item/group/option visibility, price overrides, choice rules and 50g specifications, with stable local identities and canonical source IDs. Neither mode changes existing brand rows, publication configuration, stock or POS price settings.

The editor separates **商品分類**, such as ドリンク, from per-product **追加・選択グループ**, such as 追加食材. Managers can create and rename local categories, create a base bowl, standalone food item or drink, or import individual brand products with their trusted current prices and portions. A new item's initial price is entered by the manager and interpreted using the store's existing POS tax setting. Imported prices and portions are retained at import; the local fixed price can be edited separately as described below. A base bowl may also be created from zero with the current trusted store weight rate; imported weight-priced products retain their captured per-gram rate. A new standalone item receives a store-scoped canonical row with `variable_schema.storeDineInOnly=true`; its creation, local catalog update and operation receipt commit together. The standard public menu, brand management reader and relevant compatibility reader exclude this marker, and direct brand-editor writes cannot edit, delete or reorder the store-only canonical identity. Existing brand-site and delivery readers retain their own source catalog.

Products, product categories and per-product option groups can be created and deleted inside the independent menu. The editor asks for confirmation with the target name and affected local records. Deleting a nonempty category requires another existing local category as the destination; products and their category-scoped choices move together instead of being deleted. Scope changes are isolated to moved products rather than globally relabeling shared choices, so products already in the destination keep their previous options. Deleting a product removes its exclusive group graph, while any group still referenced by another local product is retained. Deleting a group detaches it from local products. An individual option cannot be deleted if that would leave a visible required group below its minimum for any linked product; staff can deliberately delete the group instead. These operations update only the store catalog and its operation ledger. Canonical source products/options and existing order, kitchen, receipt and reprint snapshots are retained.

A new option group can begin empty, with single-choice or quantity selection. Its existing ingredient options can be imported from multiple groups in this store or from the scoped brand source, including for a product created from zero. Importing from another product or the brand copies the selected ingredient into the destination without removing it from the source. Ingredients already offered on the destination product move into its new group to avoid duplicate choices; other products keep their original choices. Imports retain their trusted price, portion, translations and canonical source identity. Heat, numbness, noodle, soup, flavor and required choices continue to be managed independently and cannot be mixed into these ingredient groups. This action does not create new freely priced canonical options or update websites/delivery menus.

After importing or arranging an option, staff can separately save its **店内の追加料金** in whole yen, including an explicit zero price. This changes only that local option's `priceDelta` and uses the existing operation identity and menu-revision guards. The source price, other local copies and other stores remain unchanged. A 50g option stays one 50g portion; two selections charge twice the new local per-portion price. Checkout, customer display and newly saved kitchen/receipt snapshots use the validated local price. Paid orders and queued reprints retain their original captured prices. Imported product prices remain unchanged by option-price editing.

### Editing existing local products

Selecting an existing fixed-price product exposes **店内の販売価格（円／1点）**, including drinks, alcoholic drinks and imported products. `setItemPrice` accepts a whole-yen amount from 0 through 9,999,999 and updates only the selected local product's sale price. It does not change the source product, another local copy, other stores, portions, option surcharges or historical order/print snapshots. A weight-priced product does not show this fixed-price form; its stored weight rate continues to determine its base charge. Changing the sales method remains a separate operation.

The product editor also provides a **商品分類** selector and **商品分類を保存**. `setItemCategory` accepts an existing category in the same store/brand catalog. The selected product's applicable choice graph moves with it without broadening the choices of other products or modifying canonical source options. Product price, portions and production identity remain unchanged. Both operations use the existing scoped permission, menu revision, operation identity and unknown-result retry flow. After saving, the form uses the returned catalog values; saving one field does not submit other unsaved form values. Names, visibility and derived local copies retain their separate controls.

### Reviewing source changes and correspondence (2026-10-21)

The independent menu retains explicit canonical source IDs. The editor's **対応・更新確認** tab lets management inspect the current source and review changes without letting brand synchronization overwrite store-owned names, prices or groups. **確認が必要な項目** includes source changes and records awaiting their first explicit review; **未取込のブランド商品・選択肢** leads to the existing import workflow. Opening or refreshing the editor only reads the comparison; it never accepts a change or initializes a review baseline. POS menu refresh remains the separate manual operation described below.

The correspondence view pairs each local product, option group and option with its current scoped source. It shows local and source names, product classification or original option group, prices and specifications. A unified store addon group may contain options from several source groups: each option retains its own source group and price instead of claiming that the whole unified group came from one group. A newly created store-only product is explicitly local-only, even if its label happens to match a brand product. Derived store versions remain linked through the existing immutable canonical IDs. The editor does not guess matches from names or repoint inventory identities.

The comparison keeps the canonical brand base price, current Web予約/website store-setting price, effective POS import price (which may contain a legacy or explicit POS override), and independent store price separate. The network-setting reference is Foundr1's current configuration; it is not evidence that an external delivery platform has already published that amount. An imported ¥650 POS option can therefore retain ¥650 locally while its brand/network reference is ¥500. Choosing to adopt the brand reference price is an explicit whole-yen local price edit; keeping the store price is equally valid. Weighted prices and per-portion prices must not be compared or adopted as interchangeable amounts.

Source changes are compared against the last imported or acknowledged **source values**, rather than against the current local values. An intentional store rename or surcharge does not repeatedly appear as a new source update. Fresh source imports capture the then-current canonical source baseline. Duplicating or regrouping an existing local copy carries its previous baseline forward, so an unread source update is not accidentally marked accepted by arranging the local menu. Older initialized menus that have no saved baseline require a first explicit review; a read cannot silently declare the current source accepted. Managers select **店内の設定を維持する** or, where compatible, **元メニューの値を採用する** for individual fields and press **選んだ項目の扱いを保存**. The keep-all action is **店内の設定を維持して確認済みにする**. Both choices acknowledge the reviewed source value for that field, while a subsequent upstream change appears again. Keeping a value preserves its local override; adopting updates only the selected local target and field. Other store copies remain independent.

An older catalog can establish its first baseline with **店内設定を維持して初回確認を完了**, keeping all current local names, prices, categories, portions, rules and identities. `acknowledgeSourceBaseline` records only source fields whose baseline is still unknown, including the currently unimported source candidates; it neither imports those candidates nor accepts a later change to an already known field. A known changed source price therefore stays pending after this action. The initial-review notice remains available after a partial per-entry review while any linked or missing local record still has unknown source fields. Opening the editor cannot perform this confirmation. The bulk operation accepts only the current trusted source revision plus the standard menu revision and operation identity, uses the same transaction guards and replay protection, and preserves the POS aggregate. A stale source or failed persistence leaves the old baseline intact.

Names, compatible fixed or option prices, and safe product classification changes may be adopted from server-read data. A gram-based option can explicitly adopt a changed gram portion; this updates only that option's captured portion metadata, retaining its price, local label and canonical identity. Until local and source portions match, source-price adoption is blocked. A 50g-to-60g change therefore never takes effect through merely acknowledging a notice or copying a price. Cross-unit conversions remain unavailable. Source group selection rules can be adopted only when the rule is bounded and coherent and existing applicable local choices satisfy its minimum; merged local-group rules, membership changes and item schema changes require individual editing. New products and options use the existing explicit import actions. A missing or retired source is visible for investigation; review neither deletes the local record nor bypasses canonical stockout, retirement or recipe checks. Required choices and source associations continue to constrain sellability.

`reviewSource` uses the existing scoped `menus.edit` and same-origin checks, a UUID operation identity, the local catalog revision and the complete current source revision. The browser submits only an entry key, field names and adopt/keep decisions; source values, prices and canonical IDs are resolved on the server. Both revisions are rechecked inside the store-locked transaction. The local change, acknowledged baseline, bounded decision history and operation receipt commit together, so a conflict or later write failure cannot partially acknowledge an update. Exact retries do not apply the decision twice. Baselines and the latest 100 decisions are additive JSON inside the independent catalog; no new table, production menu rewrite or automatic activation is required. Acknowledgement-only saves advance the management revision but do not invalidate an open POS catalog. The POS aggregate excludes review metadata and changes only when the sale-facing local catalog or enabled state changes; a separate management revision guard still rejects competing acknowledgement writes.

### Refreshing an open POS

Menu refresh is manual. After the company notifies staff of a menu change, an operator presses **メニューを更新** in the POS. There is no background menu-revision polling or automatic catalog replacement on idle, focus, visibility, network recovery or page restoration. Normal initial page loading still reads the current menu. The explicit action reads the store menu revisions and the complete catalog even if the revision values are unchanged, then applies the catalog and its revisions together and refreshes the offline menu cache. A dine-in-only change does not block an unrelated counter-takeout draft, and existing table-order settlement keeps its historical order prices.

Successful checkout, confirmed payment recovery and completed offline-order synchronization still refresh operational summaries, table checkout requests and reconciliation. For the same store they retain the current catalog, pricing settings, revisions, filters and cached offline menu. Loading a different authorized store initializes that store's menu; it must never reuse the previous store's catalog.

If the manual read detects a changed menu while a draft exists, the POS retains its displayed contents and shows an update notice in the main page, cart and product-selection dialog. Relevant known-stale additions and checkout remain blocked until staff review the update. Applying an update first reads and validates the complete catalog, then asks for confirmation before clearing unpaid products and selections. A failed read or declined confirmation leaves the draft intact; becoming idle does not apply a cancelled update. Known pending or uncertain checkout recovery and offline work must be resolved before replacement. Server-side menu-revision and expected-amount checks remain in force when staff have not yet refreshed; a rejected stale checkout must not silently reprice the cart or become another sale. Saved orders, print snapshots and reprints retain their captured prices.

### Mixed item pricing (2026-10-20 clarification)

The store/brand POS fixed-or-weight setting is a **default for base products**, not a switch for every item. Dine-in item pricing resolves in this order: drinks always sell per portion; a saved local `posPricingOverride` takes precedence; then a source item's structured `variableSchema.posWeightPricing.mode`; then only `buildable_product` may inherit the brand default. Other items default to fixed-price portions. Neither names, categories nor production/bowl classification determine the price method. Imported and existing independent snapshots created by the previous blanket rule are normalized when read, without resetting the catalog or its labels. The same pure policy is used by Store POS, both server catalog/checkout paths, source import and independent-menu resolution, including an old cached catalog used by a current client.

Managers can choose fixed or weight pricing for each non-drink item in the independent editor. `setItemPricing` changes only that mode. Choosing weight captures the current server-read store unit/rate with a source snapshot guard; a missing, zero or non-finite rate is rejected. No client-supplied rate is accepted. The saved rate remains independent of subsequent changes to the store default. Choosing fixed retains the original fixed price, which is displayed before saving; zero is allowed explicitly. Creating a new weighted item stores a zero fixed-price fallback, so switching it to fixed later uses that visible zero price. Prices of imported products and 50g specifications are not edited by this operation.

Noodle and addon choices remain `priceDelta × selected portion count`, even when attached to a weighed bowl. One mixed payment can contain a 200g base at ¥4/g, two 50g noodle portions at ¥200, two 50g beef portions at ¥650, and a ¥350 drink: ¥2,850. Only the base item carries weight measurement fields. New base products have explicit bowl production identity; ordinary new food and drink items retain their own production types regardless of price mode. Existing fixed-price bowl products retain their previously recorded kitchen/numbering identity.

The independent aggregate revision includes a pricing-policy version salt. An already-open cart from the old blanket policy must refresh/reselect before an independent-menu checkout; already-saved order recovery still returns its immutable sale. No DDL or live data rewrite is needed. Counter takeout, website and external delivery keep their existing fixed-price and source-catalog boundaries.

For a selected product, staff can create an optional unified addon group and explicitly select options from several existing optional groups. Known heat, numbness, soup, noodle, medicinal, flavor, drink and required groups remain separate. Selected options move only for that product; a shared group's remainder is isolated so another product retains its original choices. Canonical option IDs prevent duplicate imports, and each option retains its source group identity and source specification snapshot. Staff can add more options later and save the group's display order. Quantity controls preserve multiple portions: two selections of a 50g option are two original-price portions, not a new portion size. A move or reorder cannot supply a different price or alter the brand source.

Store names and translations belong to the independent catalog. Renaming a Japanese/source label clears its copied foreign-language names so an old brand translation cannot silently display the previous label. Existing translations remain intact on unrenamed copies. A derived item receives its own local identity and copies item-specific option groups/options with fresh local IDs; shared store option groups remain explicitly shared. Source IDs preserve the existing SKU/recipe association rather than creating another inventory ledger or matching records by name.

Only POS dine-in uses an enabled independent menu. Checkout validates the local catalog and revision on the server, keeps canonical source IDs for existing inventory/recipe readers, and saves the local menu identity and charged labels as order snapshots. A unified addon group is split back into its canonical source groups in persisted customizations while retaining the local display group and option labels; this preserves existing inventory normalization and prints the configured group with the correct portion count. Customer display, kitchen/finishing/pickup tickets and receipts use validated labels. Later menu renames do not rename a paid order or a queued reprint. Existing stockout and source-identity checks still apply; an independent label must not make an unavailable source sellable. Retiring the canonical source product or its required option therefore blocks the corresponding store versions until a manager reviews that association. New standalone items have their own store identity; importing or regrouping an existing SKU does not create another inventory ledger. Existing brand-based dine-in payment rules remain unchanged.

`/api/os/menus/dine-in` requires the existing `menus.edit` permission, active store scope and active store-brand membership. Writes require the same origin, the previously read revision and a UUID operation identity. Stale competing edits are rejected; retrying the same operation with the same body returns its saved result without another copy or rename. Source import is guarded against a concurrent source/POS configuration change. No shared Uber-authority restriction is relaxed.

`db/migrations/20261020_store_dine_in_menu.sql` adds the independent catalog and operation ledger without initializing any store. Apply it only to an authorized target before activation. If the schema is absent, management reports that the database update is required and existing unconfigured POS behavior remains available. Other database errors must not silently fall back to a different priced catalog. Offline work created before activation or a catalog change must be reconciled explicitly; it cannot silently adopt new names or prices.

This development task prepares the implementation and isolated verification. Production migration, menu initialization and publication are separate actions; do not infer live activation from this document.

### Store item and option-group associations

The independent editor exposes the same store-only relationship from both directions: a product selects the option groups it uses, and an option group selects the products that use it. Both save the product's ordered `optionGroupIds`; choosing no products leaves the group and its options available for later reuse. Unlinking is distinct from hiding or deleting. A shared group's name, prices, options and selection rules apply to its associated products; copying a group through whole-group import still creates an independently editable version.

Association saves validate the active store/brand and existing local identities, preserve retained display order, and append newly selected groups. They use the existing operation identity, revision and transaction guards. Existing menus are not rewritten at deployment. When an existing group is explicitly linked to new products, retain the effective option restrictions of its existing consumers; newly associated products receive the selected group's choices. Source SKU activity, stock availability, required-selection rules and trusted option lineage remain checkout requirements. Existing paid-order and print snapshots remain immutable.

The unified ingredient importer can collect selected optional ingredients from several source groups into a new X group or an existing eligible store group, including an imported optional ingredient group. Heat, numbness, soup, noodle, flavor and required choices retain separate groups. The import picker shows the source group and origin, supports search and folding, and distinguishes a new target from an existing target. A single-product target retains the existing move-for-that-product behavior; importing into a shared or unassigned target copies the selected options without moving any other product's selections. Duplicate canonical source options are not imported twice. Portion sizes and prices are carried over unchanged, with subsequent local price edits remaining explicit.

These writes affect only the independent store catalog. The brand master, website, Web予約 and external delivery associations are unchanged. The POS menu remains manually updated; reloading a menu does not rewrite an unpaid sale or an old offline request.

## Per-category and per-product POS fulfillment

Independent store menus can choose **提供方法** for a product category and override it for a particular product. The category's **通常（調理・呼出し）** leaves its optional `fulfillmentMode` unset and resolves to `prepare`. A product's **分類設定を引継ぐ** leaves its field unset and follows the category with the same brand and exact category name. Explicit `prepare` or `immediate` overrides that category. The editor saves through `setFulfillmentMode`, using the existing store/brand permissions, revision check, operation identity and transaction; no database column or shared-menu edit is introduced.

**会計時にお渡し** is for goods actually handed to the customer at payment, such as a counter condiment or sealed drink. It excludes that product from preparation/pickup work and preparation tickets while preserving its financial line and receipt. Actual bowl products always resolve to preparation: the API rejects an immediate override on a bowl or on a category already containing bowls. Category and product defaults do not assume that every drink is ready-made; existing unset values continue to require preparation.

These are store POS settings. Shared website/delivery menu definitions, existing price/portion/option rules and historical order/print snapshots remain independent. A category rename, product duplication or archive/restore preserves the explicit setting; moving an inheriting product follows its new category. New products inherit their category. Runtime projections expose the resolved mode, including product-backed choices, without replacing the stored inheritance marker. Cashiers still apply changed POS menus manually. Production activation and end-to-end checkout/output verification are recorded by the release, separately from these menu-editor contracts.
