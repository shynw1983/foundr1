# 外卖菜单发布规则基准

更新日期：2026-08-15

## 目的

Foundr1 OS Menu 是商品、分类、自定义组、选项、价格和多语言内容的唯一主数据源。网站预约直接读取 OS 的结构化菜单；Uber Eats、Rocket Now 和出前馆由 OS 生成平台专用菜单，再由 API 或 Desktop Bridge 执行并回读验证。

本文先记录当前四个平台实际正在使用的内容。所有内容分为三类：

- **已确认**：已从线上 OS 数据或已登录的平台后台读取。
- **建议规则**：根据当前菜单拟定，实施前仍可调整。
- **待确认**：后台没有直接显示，或属于经营策略，需要另行决定。

## 盘点来源

- Foundr1 OS 线上数据库中的まぁ麻菜单、选项组、价格及翻译字段。
- Uber Eats Menu Maker 当前商品、价格、分类、自定义组和商品编辑页面。
- Rocket Now Manager 当前菜单、选项、价格和选择数量设置。
- 出前馆管理后台当前菜单、价格、分类和品切れ终売页面。
- Foundr1 中保存的 Uber 菜单映射与 2026-08-11 菜单快照。

本次盘点只读取后台，没有修改平台菜单。

### 语言结论

目前三个外卖后台都没有在现有商品编辑资料中使用独立的多语言字段：

- Uber 当前把日语、简体中文、韩语和英语拼接在同一个品名中。
- Rocket 当前商品名、选项名和说明均以日语为主。
- 出前馆当前把日语、简体中文、韩语和英语拼接在同一个名称中。

因此第一阶段发布规则应复制当前呈现方式，不应假设平台会根据顾客语言自动切换。平台是否提供未启用的原生本地化能力，需要单独验证后才能更改规则。

OS 的目标语言为日语、英语、简体中文、繁体中文、韩语、越南语和尼泊尔语。当前まぁ麻线上数据完整度如下：

| 数据 | 总数 | 简中 | 繁中 | 英语 | 韩语 | 越南语 | 尼泊尔语 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 商品 | 21 | 15 | 0 | 15 | 15 | 0 | 0 |
| 选项 | 175 | 171 | 64 | 171 | 171 | 70 | 70 |

这意味着完整菜单同步之前，必须先补齐翻译或明确回退策略。建议回退顺序保持为：请求语言 → 英语 → 日语原名。

### 已确认的价格现状

- 网站和出前馆目前属于基础价层级。
- Uber 和 Rocket 目前属于高价层级，样本价格完全一致。
- 高价层级大致相当于基础价的 1.25 倍，但现有价格包含 `¥415`、`¥216`、`¥2,222` 等特殊尾数，不能仅凭一个普通取整公式完全还原。
- 现有 Uber 导入规则使用 `OS 价格 = Uber 价格 × 0.8 后按 10 日元取整`。这是从平台价反推基础价，不等于已经确定了未来从基础价生成平台价的规则。

### 建议的价格模型

OS 应保存：

- `basePrice`：网站和标准经营价格。
- `platformPricingRule`：平台默认倍率、取整方式和取整单位。
- `platformPriceOverride`：需要保留特殊尾数或特殊经营策略时的覆盖价格。

第一阶段迁移时建议：

1. 把现在各平台的实际价格保存为平台覆盖价格，保证首次同步不改价。
2. 新商品默认使用平台公式生成建议价格。
3. 发布前显示各平台计算结果，由负责人确认。
4. 等经营方确定统一取整策略后，再逐步减少覆盖价格。

### 待经营决策

- Uber 和 Rocket 是否正式统一为基础价的 1.25 倍。
- 新价格按 1 日元、5 日元、10 日元还是心理价尾数取整。
- 商品与 Topping 是否使用相同倍率。
- 出前馆是否长期保持网站基础价。
- 堂食、Web 预约、外带和配送价格是否需要分别保存。

### Uber 当前结构

- Standard Topping 保持为一个组，当前有 47 个选项。
- 后台当前规则为最多选择 100，同一选项最多选择 10 次。
- Basic 有 24 个平台选项，Premium 有 28 个，VIP 有 9 个。
- 商品可分别设置配送价和外带价，并可另外启用 Webshop 价格。

### Rocket 当前结构

- Rocket 当前只显示日语名称。
- Standard Topping 已拆成两组：第一组最多 35，第二组最多 13。
- Basic 当前最多 24，Premium 最多 20，VIP 最多 3。
- 面类最多 2，变更面最多 2，冷面最多 1且必选。
- Rocket 平台现有 Standard 两组共显示 48 个位置，而 OS 当前 Standard 为 47 项。正式发布前必须识别多出的旧选项，不能直接覆盖或删除。

### Rocket 拆分建议规则

Rocket 的拆分应由 OS 的平台转换器完成，不由 Bridge 临时判断：

1. 按 OS 排序取得组内选项。
2. 根据 Rocket 已验证的每组容量拆分。
3. 第一组保留原名称，后续组命名为 `2`、`3`。
4. 每组保存稳定的平台组映射 ID。
5. 一个原料缺货时，所有拆分组中的同一稳定选项 ID 一起更新。
6. 选项移动到另一拆分组时，发布预览必须显示“移动”，不能显示成无提示删除再新增。

第一阶段沿用目前已经验证的 Standard `35 + 其余` 拆分方式。其他组只有超过平台容量时才拆分。

### 出前馆当前结构

- 当前库存页面共显示约 214 条商品及选项记录。
- 菜单编辑页面当前有 7 个分类、21 个商品尺寸记录。
- 商品、选项在库存页面中使用同一套品切れ／终売操作。
- 当前永久缺货必须选择 `終売`，不能使用“本日中”的品切れ。
- 当前名称为四语言拼接；部分临时或旧商品仍只有日语，发布前需要差异检查。

出前馆自定义组的后台容量限制仍需通过一个不保存的编辑预览进一步确认。在确认之前，不得自动改变现有组结构。

## 平台发布转换规则

### 网站预约

- 直接读取 OS 公共菜单 API。
- 按顾客语言读取结构化 `displayNames`。
- 使用 OS 基础价。
- 不拼接多语言名称。

### Uber Eats

- 第一阶段沿用当前 `日语｜简中｜韩语｜英语` 名称。
- 使用 Uber 平台价格覆盖；没有覆盖的新商品再使用待确认的高价公式。
- 保留单一大组结构，例如 Standard 47 项。
- 同步商品、分类、说明、图片、配送价、外带价、自定义组和售罄状态。

### Rocket Now

- 第一阶段沿用当前日语名称和日语说明。
- 默认镜像 Uber 高价层级，但价格仍独立保存，避免未来平台策略分开后互相影响。
- 自动执行组容量拆分，Standard 先按当前 `35 + 其余` 规则生成。
- 缺货使用“非表示”，恢复使用“解除”。

### 出前馆

- 第一阶段沿用当前 `日语｜简中｜韩语｜英语` 名称。
- 默认使用基础价层级。
- 保留现有分类和商品尺寸结构，直到自定义组容量确认完成。
- 缺货使用 `終売／无期限`，恢复使用设置解除。

## 同步流程和状态

菜单编辑不能在每次键入时直接发布。建议采用草稿和发布流程：

1. OS Menu 保存草稿。
2. 生成四个平台的目标菜单。
3. 与平台当前菜单进行差异比较。
4. 显示新增、改名、改价、移动、停用和删除数量。
5. 用户确认发布。
6. 为每个平台建立独立任务。
7. Bridge 或平台 API 执行。
8. 重新读取平台后台并逐项验证。
9. 保存最终结果和平台映射 ID。

每个平台至少需要以下状态：

- 等待生成
- 规则校验中
- 等待 Bridge
- 正在同步
- 正在验证
- 同步成功
- 部分成功
- 重试中
- 超时
- 需要重新登录
- 找不到平台对象
- 平台限制不允许
- 验证不一致
- 同步失败

失败任务必须支持单平台重试和单条重试。已经成功的平台不能因为另一个平台失败而重复执行。

## 安全规则

- 首次完整发布只允许新增和更新，不自动删除平台现有对象。
- 删除、停用、隐藏必须在差异预览中单独确认。
- 平台对象优先使用稳定 ID 对应，名称仅作为迁移和异常恢复的辅助匹配。
- 平台手工修改后，OS 应显示“平台漂移”，不能静默覆盖。
- 每次发布保存发布前快照、目标快照、执行结果和验证结果。
- 平台规则版本化；规则变化不能自动重算并发布旧菜单。
- Bridge 只保存登录会话和页面执行逻辑，不保存菜单主数据或经营价格规则。

## 已发现的数据问题

- OS 商品翻译尚未覆盖繁中、越南语和尼泊尔语，部分商品连简中、英语和韩语也缺失。
- 选项翻译覆盖率较高，但繁中、越南语和尼泊尔语仍不完整，个别翻译混有日语。
- Rocket Standard 当前比 OS 多一个平台位置，需要确认是重复项还是平台专用项。
- Uber 当前存在少量未挂接分类或自定义组的旧商品，需要发布前建立“保留、归档或删除”清单。
- 三个平台目前同时存在纯日语名称和多语言拼接名称，不能直接批量统一而不做差异预览。

## 实施顺序

1. 补充平台规则数据结构和版本字段。
2. 导入并冻结当前平台对象 ID、当前价格和组映射，作为迁移基线。
3. 建立只读差异预览，不执行修改。
4. 完成语言缺失检查和发布阻止规则。
5. 实现价格投影与平台覆盖价格。
6. 实现 Rocket 组拆分投影。
7. 实现商品、选项和分类的新增／更新同步。
8. 加入回读验证、进度、超时和重试。
9. 最后开放停用和删除同步。
